# 모델별 배치 실력 측정

AI가 자리를 정하는 그림 7종(클래스도·패키지도·컴포넌트도·배치도(deployment diagram)·유즈케이스도·상태도·액티비티도)을 Claude 모델이 cysUML 검사에 합격할 때까지 고쳐 그리는 데 **몇 번·얼마·몇 초**가 드는지 쟀다. 교류도는 cysUML이 배치하므로 뺐다.

## 어떻게 쟀나

1. **문제:** 요소와 관계만 주고 자리(`left`·`top`·`via`·`width`·`height`·`name_side`)는 지운다. 모델이 모든 자리를 정한다.
2. **실행:** 문제 하나를 `claude -p --bare`로 한 번 돌린다. 도구는 cysUML MCP 그림 도구만 주고, "검사에 합격하면 멈추고, 아니면 고쳐서 다시 그려라(최대 10번)"라고 지시한다. 실행마다 비용 상한(`--max-budget-usd`)을 건다 — readme·hard 묶음은 $3, xl은 $5, xxl은 $4로 걸었다. 상한은 측정을 이어 가며 정했다. 그림이 커진 xl에서 $5로 올렸고, xxl은 전체 비용을 묶어 두려고 $4로 낮췄다.
3. **판정:** `stream-json` 출력에서 그 문제의 그리기 도구 호출만 그린 차례로 세고, 차례마다 검사 결과에서 판정 머리(`합격`·`불합격`·`입력 오류`·`그림이 너무 커서`)로 시작하는 첫 줄을 읽는다. 저장에 실패하면 서버가 그 오류 글을 검사 요약 앞에 붙이는데, 이때도 판정은 요약으로 하고 저장 실패 횟수는 따로 적는다. 10번째 그림 안에서 한 번이라도 `합격`이면 합격이고, 몇 번째 그림에서 처음 합격했는지 적는다. 지시를 넘겨 더 그리다 합격한 것은 불합격으로 친다. 검사에 합격했어도 그 차례에 보낸 입력이 문제와 다르면(자리 칸을 뺀 어느 칸이든 빼거나 더하거나 바꾸면) 합격으로 치지 않고 `changed`로 적는다 — 문제를 쉽게 바꿔 합격하는 것을 막는다. 두 입력은 cysUML이 직접 읽은 꼴(빠진 `kind`·`navigable`에 기본값을 채우고, `id`·이름으로 가리킨 요소를 푼 것)로 견주고, 자리 칸과 `id`는 보지 않는다. 이름은 줄을 어디서 나눴든 같은 이름으로 본다. 줄 바꿈 자리는 문제·그림 어느 쪽에서든 띄어쓰기로도, 붙여 쓴 것으로도 본다. 한 줄 안에서 띄어쓰기를 더하거나 뺀 이름(`Order Service`와 `OrderService`)은 다른 이름이다(이어진 공백은 하나로, 앞뒤 공백은 없는 것으로 본다). 이름이 하나뿐인 요소는 이름으로 가리키고, 이름 없는 점·마름모와 이름이 겹치는 요소는 이웃(들고 나는 관계, 담긴 곳)으로 가리켜 `id`를 어떻게 바꿔 써도 같은 그림이면 같게 보고, 흐름을 바꿔 이으면 다르게 본다. 연관은 양 끝을 바꾸면서 다중도·방향도 함께 맞바꿔 적은 것을 같은 그림으로 본다. 모델을 잰 것이 아닌 실행은 불합격으로 치지 않고 표에서 빼 따로 적는다: cysUML MCP 서버가 붙지 않았거나 그리는 도중 끊겨 그 차례로 끝남(`mcp_failed`), claude가 시작하지 못함(`no_init`), 한 번도 그리기 전에 시간이 다 감(`no_answer`), 서버 쪽 API 오류(인증·없는 모델·크레딧 부족·429·5xx·연결)로 10번을 다 그리기 전에 끊김(`api_error`), 끝의 결과 이벤트 없이, 또는 claude 안의 오류(`error_during_execution`)로 끝남(`no_result`, 크래시 등 — 종료 코드와 상관없이), cysUML 도구가 예외를 내거나 답하지 않아 그 차례로 끝남(`tool_error`), 측정 스크립트 오류(`harness_error`), 멈출 때 결과를 내기 전에 끊김(`stopped`, CSV에는 들지 않고 `row.json`에만 남는다). 이번 609번에는 이런 실행이 없다. `--max-turns`는 14로 넉넉히 두어 모델이 10번을 넘겨 더 그릴 수도 있고, 그렇게 더 그린 비용도 실행 비용에 든다(잴 방법을 바꾸지 않으려고 그대로 두었다). 비용·시간은 실행 끝의 결과에서 한 번 읽는다.

effort는 Claude Code `--effort`로 주는 값으로, 모델이 얼마나 깊게 생각하는지를 정한다(low·medium·high).

환경: cysUML 0.2.1(`main` f2fb245), Claude Code 2.1.327, MCP Python SDK 2.3.0, 2026-11-18 측정. 모델은 `claude-haiku-5-5`·`claude-sonnet-5-5`·`claude-opus-5-5`·`claude-fable-5-2`. 비용은 Claude API 요금 기준이다.

묶음은 대략 요소 수로 나눴다(hard와 xl은 14개에서 겹친다).

## 결과

readme 묶음은 문제마다 1번, 나머지 묶음은 문제마다 3번씩 돌렸다. Haiku high만 xxl을 5번씩 돌렸다 — 가장 싼 모델도 가장 큰 그림에 합격하는지 더 확인하려고 문제마다 2번씩 더했다. effort는 readme를 high로만, hard·xl을 low·medium·high로, xxl을 high·medium으로(Haiku는 high로만) 쟀다. 아래 표의 실행은 모두 609번이고, 비용은 모두 $160.85였다.

판정 규칙(10번 상한, 그 문제의 도구만 세기, `changed`)은 잰 뒤에 다듬었다. 아래 표는 잴 때 남은 `stream.jsonl`을 지금 규칙으로 `rescore.py`가 다시 읽은 값이다. 그래서 바뀐 실행은 열둘이다. 10번을 넘겨 합격한 Haiku low 1번과, `changed` 차례가 난 11번이다. 바꾼 것은 이렇다.

- 클래스도·패키지도의 연관에 `navigable: none`을 달아 화살촉을 모두 없앰 7번: Sonnet `modules-xl` 4번, `lms-xxl` 1번, Haiku `lms-xxl` 2번
- Opus low `order-life` 2번: 상태의 동작 줄을 뺌
- Haiku high `billing`: `component_icon`을 `component`로 바꿈
- Sonnet medium `subscription-xl`: 관계 하나를 바꿈

`changed` 차례가 난 11번 가운데 Opus low 1번은 다시 그려 두 번째 그림에 합격했고, 나머지 10번은 불합격이 되었다. 여기에 10번을 넘겨 합격한 Haiku low 1번을 더해, 다시 읽어 불합격이 된 실행은 열하나다.

## 읽는 법

- **요소 36개까지 대부분의 실행이 합격했다.** 위 두 비용 표(겹치는 high 칸은 한 번만 세어)의 609번 가운데 불합격은 15번이다. 그림을 바꿔 그린 10번(Sonnet 6번, Haiku high 3번, Opus low 1번), effort를 낮춘 Haiku 4번(그중 hard low 한 번은 12번째 그림에서 합격해 최대 10번을 넘김), 비용 상한에 걸린 Fable high 1번이다. 26개 문제 가운데 25개는 네 모델 모두 한 번 이상 합격했고, 남은 하나는 Haiku가 한 번만 돌린 `billing`이다.
- **검사만으로는 그림을 바꿔 그린 것을 못 막는다.** 검사에 합격한 차례 606번 가운데 11번은 그림을 바꾼 것이었다(`changed`). 7번은 클래스도·패키지도의 연관에 `navigable: none`을 달아 화살촉을 모두 없앤 것이고(Sonnet 5번, Haiku 2번), 화살촉끼리 부딪치는 불합격을 피하는 지름길이다. 검사는 그린 그림의 겹침만 보고, 그 그림이 주어진 모델과 같은지는 모른다. Opus 5.5 high·medium과 Fable 5.2는 한 번도 그림을 바꾸지 않았다.
- **모델 차이는 "몇 번 만에"에서 난다.** effort high에서 합격까지 평균 그림 수는 Fable 1.1\~1.2번, Opus 1.2\~1.4번, Sonnet 1.2\~2.4번, Haiku 1.2\~2.5번이다.
- **그대로 그린 합격이 꼭 필요하면 Opus 5.5 high다.** 60번 모두 합격했고 그림을 바꾼 적이 없다.
- **싸게 쓰려면 Haiku 5.5 high가 낫다.** high에서 66번 중 63번 합격했고(놓친 셋은 모두 그림을 바꿈) 실행 한 번에 $0.003\~0.11이다. effort를 낮춰도 비용은 거의 같았고(hard $0.013\~0.015, xl $0.02\~0.03), 요소 11개 이상 그림에서 불합격이 생겼다(xxl은 high만 쟀다). 대신 가장 여러 번 고쳐 그린다.
- **effort를 같게 두고 견주면 Sonnet 5.5가 가장 빨랐다**(hard low 29초·medium 33초·high 42초, xl 51초·58초·108초, xxl medium 143초). 예외는 둘이다. readme high는 Fable과 같은 14초였고, xxl high는 Haiku가 293초로 가장 빨랐다(Haiku만 15번 평균).
- **effort를 낮추면 모든 칸에서 빨라졌다.** 첫 그림 합격은 hard·xl에서 대체로 줄었지만(Sonnet은 high에서 low로 hard 12/24→7/24, xl 7/18→2/18), xxl에서는 Sonnet·Opus가 반대로 medium이 high보다 많았다(Sonnet 3/9 대 0/9, Opus 6/9 대 5/9). xxl의 Fable은 6/9에서 5/9로 줄었다. xxl의 Sonnet은 medium이 high보다 첫 그림 합격·비용($0.35 대 $0.63)·시간(143초 대 334초) 모두 나았다.
- **첫 그림에 맞히는 게 중요하면** 첫 그림 합격이 가장 많은 것은 Fable 5.2 high다(52/60). Fable 5.2 medium은 그 절반쯤의 비용으로, 요소 11\~23개 그림(hard·xl)에서 비용이 비슷한 Opus 5.5 high보다 첫 그림 합격이 많고(hard 20/24 대 17/24, xl 15/18 대 12/18) 빨랐다(hard 36초 대 66초, xl 76초 대 162초). 30개가 넘는 그림에서는 Opus 5.5 medium이 Fable 5.2 high와 같은 첫 그림 합격(6/9)을 절반이 안 되는 비용($0.73 대 $2.41)으로 냈다. 이 그림에서 Fable high의 평균에는 상한에 걸린 실행 둘(각각 $4.03, $6.03)이 들어 있어, 둘을 빼면 $1.67이고, Opus 5.5 medium의 비용($0.73)은 그 0.44배다.

## 한계

- 문제마다 대개 3번이라 몇 번 차이는 우연일 수 있다.
- 실행마다 Claude Code `--bare`의 시스템 문서와 cysUML 도구 설명(약 3.7만 토큰)이 붙는다(캐시됨). 비용은 Claude API 요금 기준이라 다른 MCP 클라이언트나 구독 요금제에서는 다를 수 있다. effort를 고르는 방법도 클라이언트마다 다르다.
- 문제 글은 영어이고 cysUML의 도구 설명·검사 결과는 한국어다.
- 잴 때는 셸 환경 변수와 사용자 설정 파일을 막지 않았다(지금 `run_bench.py`는 허용한 변수만 넘기고 `--setting-sources ""`로 설정 파일을 읽지 않는다). 그때 셸에는 `CLAUDE_EFFORT=xhigh`, 설정 파일에는 모델별 effort(Opus 5.5 xhigh, Fable 5.2 high)가 있었다. 실행 기록에 실제로 쓰인 effort가 남지 않아 확정할 수는 없지만, 모든 모델에서 effort가 오를수록 시간이 차례로 늘어(예: Opus hard low 33초·medium 50초·high 66초) `--effort` 플래그가 적용된 것으로 본다.
- 그림을 바꿨는지 보는 대조는 이름 없는 요소를 이웃으로만 가린다. 그래서 이름 없는 요소끼리 대칭으로 이어진 모양(예: 이름 없는 합류 마름모 6개의 고리를 3개짜리 고리 둘로 바꿈)은 바뀐 것을 놓칠 수 있다. 이번 문제의 이름 없는 요소 43개는 39개가 이름 있는 요소에 바로 닿고, 나머지 4개는 그 그림에 하나뿐인 끝 점이라 이런 모양이 없다. `run_bench.py`는 이런 모양이 될 수 있는 문제(이름 있는 요소에 닿지 않고 종류도 겹치는 이름 없는 요소가 있는 문제)를 시작할 때 알린다.
- 문제를 쓸 때 도구 규칙을 지켜야 한다. 처음 쓴 hard의 `services`는 원 하나에 소켓 둘을 강제해 풀 수 없었다(도구 설명: "소켓은 한 원에 하나다"). 둘째 쓰는 쪽을 의존 화살표로 고친 뒤 잰 값만 위 표에 넣었다.

## 다시 재기

필요한 것: `PATH`에 `claude`(Claude Code), `uv sync`로 만든 `.venv`(MCP 서버를 `.venv/bin/cysuml`로 띄우므로 macOS·Linux 기준), Claude API 키.

다시 재면 그때 작업 사본의 cysUML 코드와 `docs/images/` 입력 파일로 잰다. 위 표를 잰 0.2.1(`f2fb245`)에는 아직 `bench/`가 없었으니, 같은 버전으로 재려면 `git worktree add <경로> f2fb245`로 그 커밋을 꺼내 지금 `bench/`를 그 안에 복사하고, 그 안에서 `uv sync` 뒤 돌린다.

```sh
uv sync
# API 키는 ANTHROPIC_API_KEY, 없으면 BENCH_KEYCHAIN_SERVICE로 지정한 맥 키체인 항목에서 읽는다.
# --bare라 Claude 구독 로그인은 쓰지 않고, 비용은 그 키의 Claude Console 조직에 붙는다.
# 키를 명령에 바로 쓰면 셸 기록에 남으니 키체인에 넣어 두고 이름만 준다.
# --budget은 실행 한 번의 비용 상한(달러)이다. 위 표는 readme·hard $3, xl $5, xxl $4로 쟀다.
BENCH_KEYCHAIN_SERVICE=<키체인 서비스 이름> uv run python bench/run_bench.py --models claude-sonnet-5-5 --efforts medium --problems hard --runs 3 --budget 3 --tag hard-sonnet-medium
uv run python bench/summarize.py ~/Documents/cysUML-bench-runs/hard-sonnet-medium/results.csv
uv run python bench/inspect_run.py ~/Documents/cysUML-bench-runs/hard-sonnet-medium/claude-sonnet-5-5_medium/shop/run1/stream.jsonl
```

- `--problems`에는 문제 이름이나 묶음 이름(readme·hard·xl·xxl)을 준다.
- 위 표를 모두 다시 재면 Claude API 요금으로 약 $161이 든다(표의 609번 합계).
- 기록은 `--out`(기본 `~/Documents/cysUML-bench-runs/`) 아래 `--tag`(기본은 시작한 `월일-시분초`) 폴더에 남는다. 실행마다 문제 글·`stream.jsonl`·그린 그림이 있고, 묶은 `results.csv`가 맨 위에 있다. 이미 기록이 있는(빈 폴더가 아닌) 태그로는 돌지 않는다.
- `results.csv`는 실행이 끝날 때마다 한 줄씩 쓴다. Ctrl-C(또는 `kill`, 터미널 닫기)로 멈추면 남은 실행은 띄우지 않고 돌던 claude도 끝내며, 끝난 실행까지는 남는다. 정리가 오래 걸리면 2초 넘어 한 번 더 보내 바로 끝낼 수 있다(그 안에 다시 온 같은 신호는 같은 신호로 본다 — `uv run`은 받은 신호를 한 번 더 넘긴다). 키·크레딧 오류나 시작 실패로 스스로 멈추는 중이면 첫 신호에 바로 끝낸다. API 키가 틀리거나(401) 크레딧이 떨어지면 바로 멈춘다. 없는 모델 이름(404)이나 권한 오류(403)가 난 모델은 그 모델의 남은 실행만 빼고 끝날 때 종료 코드 1로 알리며, 403이 두 번째 모델에서도 나면 키·조직 전체의 권한 문제로 보고 멈춘다. 잰 실행 없이 claude가 시작하지 못하거나 MCP가 붙지 않은 실행이 3번 나와도 멈춘다. `--timeout`을 넘겨 끊긴 실행은 `timeout`으로 적고, 비용은 알 수 없어 합계에 들지 않는다. 한 번 이상 그린 뒤 시간이 다 간 실행은 API가 멈춘 것과 모델이 오래 생각한 것을 기록으로 가를 수 없어 모델의 불합격으로 센다(이번 609번에는 시간 초과가 없다).
- 판정 규칙을 고친 뒤에는 `uv run python bench/rescore.py <태그 폴더>`가 남은 `stream.jsonl`을 지금 규칙으로 다시 읽어 같은 폴더에 `rescored.csv`를 쓴다(다시 재지 않으니 돈이 들지 않는다). 문제는 지금 문제 파일이 아니라 그 실행의 `prompt.txt`에 실제로 들어간 것과 견준다. 위 표는 이 `rescored.csv`로 냈다.
- `summarize.py`는 준 CSV를 모델·effort별로 묶는다. 위 "묶음별" 표처럼 묶음마다 보려면 묶음마다 태그를 나눠 돌리고 그 `results.csv`를 하나씩 준다. 합계 줄의 비용 범위는 묶음별 평균에서 손으로 골랐다.
