# 워크트리 잔재와 제거 절차

`/issue` 2단계에서 `residue.sh` 가 `RESIDUE` 를 냈을 때, 그리고 7단계 머지 후처리가 (b)~(d)에서
부른다. 둘이 같은 절차를 쓰므로 여기 한 곳에만 적는다 — 전에는 두 벌이었고 이미 어긋난 적이 있다.

`<스킬 디렉터리>` 는 SKILL.md "이 스킬의 파일"이 알려준 절대경로이고, 스크립트를 부르는 법(한 줄로
친다, 첫 줄이 판정이다, 종료 코드가 0이 아니면 멈춘다)도 거기 있다. 워크트리 제거 절차에 들어선 뒤에는 그
세션이 끝날 때까지 그 절차 앞머리에서 떠 둔 `<사본>` 으로 읽는다 — 이 문서 밖(SKILL.md 6단계)에서 부르는
자리도 같다. `<레포 루트>` 는 SKILL.md 2단계(또는 7단계 시작)에서 구한 본 체크아웃 경로다.

## 먼저 알아 둘 것

- **스냅숏 파일은 `<레포 루트>/scratchpad/wt-<평탄화한 브랜치명>.z` 다**(평탄화 = `/` → `+`). 아래에서
  `<스냅숏>` 이라 부른다. `find.sh` 가 부를 때마다 워크트리 목록을 새로 떠 덮어쓰고, `suffix.sh` 가
  그것을 읽고, `verify-removed.sh` 가 remove 직전 기준선으로 쓴다. 자리를 바꾸지 않는다:
  - **지울 워크트리 안에 두면 안 된다** — remove 가 스냅숏까지 지워 사후 확인을 못 한다. 본 체크아웃의
    `scratchpad/` 는 gitignore 라 남아도 아무것도 막지 않는다(그 줄은 이 스킬을 들여온 커밋이 `.gitignore` 에 넣었다 —
    본 체크아웃이 그 전 커밋에 서 있으면 `git status` 에 추적 밖 파일로 보인다).
  - **이름에 브랜치명을 넣는다** — 여러 `/issue` 세션이 동시에 돌 수 있어서, 고정 이름이면 남의 스냅숏으로
    판정한다.
- **`branch-escaped` 줄의 브랜치는 이 문서 어디서도 브랜치 이름으로 옮기지 않는다.** "그 브랜치로 … 돈다",
  "블록의 `branch` 줄에서 옮긴 브랜치로", "그것이 쥔 브랜치 이름으로" 같은 문장은 모두 `branch` 줄에만 해당한다.
  `branch-escaped` 는 명령에 넣을 수 없는 이름이라(SKILL.md "인자는 큰따옴표로 감싼다") 이어받기·잔재 정리·제거
  절차 어느 쪽으로도 이 워크플로가 그 브랜치를 다루지 않는다 — 줄을 그대로 보고하고, 그 브랜치를 어떻게 할지(이름을
  바꾸거나 치우거나, 이 이슈와 무관하면 그대로 두거나)는 사람이 정한다. 이 스킬이 만드는 이름이 아니니 남의
  브랜치다 — 번호가 우연히 겹쳤을 수 있다. 위 스냅숏 이름에도 그 이름을 넣지 않는다 — 스냅숏 경로는 `find.sh` 가
  돌기 전에 셸이 펼친다.
- **앞선 세션의 꼬리가 딸려 왔으면 그 `remove` 의 사후 확인부터 한다.** 꼬리는 "앞선 세션이 remove 까지 했고
  사후 확인은 못 했다. 스냅숏 …, 대상 …" 꼴로, 제거 절차 3번 "멈출 때"가 새 세션을 그렇게 부르라고 시킨 것이다.
  `머지했어 <레포 이름> PR #…` 로 왔든 `/issue <이슈번호> <레포 이름>` 으로 왔든(레포 이름이 빠졌어도 같다)
  **레포 루트를 구해 확인한 직후, 다른 어떤 스크립트보다 먼저** 돌린다 — 2단계면 `residue.sh` 전, 7단계면 (a)
  전. 늦추면 두 갈래에서 확인이 빠진다: `find.sh` 가 돌면
  (잔재 조사·이어받기 1번·제거 절차 0번 ③) 스냅숏이 새 목록으로 덮어써져 영영 못 하고, `residue.sh` 가 `CLEAN`
  이면(앞선 세션이 이름을 받아 등록만 남은 워크트리를 지운 경우 — 브랜치 ref 가 없어 잔재로 안 잡힌다) 확인 없이
  새 워크트리로 가 버린다. 아직 이 세션에서 지운 것이 없으니 `<스킬 디렉터리>` 로 친다:

  ```
  bash "<스킬 디렉터리>/scripts/verify-removed.sh" "<스냅숏>" "<대상 path>"
  ```

  값은 **부른 문구에 딸려 온 것**을 그대로 옮긴다. `REMOVED` 면 그 사실을 보고에 적고 입구의 절차를 그대로 이어
  간다(제거 절차까지 가면 0번 ③은 `NONE` 을 내 1~3번을 건너뛰고 4번부터 간다 — 지름길을 따로 두지 않는다).
  `STILL_PRESENT`·`REREGISTERED` 면 제거 절차 3번 "사후 확인"의 그 갈래대로 멈추고 보고한다. **종료 코드가 0이
  아니면 멈추고 stderr 를 보여준다**(SKILL.md 규칙 그대로) — 기준선이 아닌 스냅숏(경로가 0개나 2개 이상), 없거나
  빈 파일, 잘못 옮긴 경로가 다 같은 3 으로 오므로 가르지 않는다. **두 값 중 하나라도 문구에 없으면 이어 가지 않고
  멈춘다** — 앞선 세션의 보고에 있는 스냅숏 경로와 대상 path 를 그대로 붙여 달라고 한다. 확인 없이 이어 가면 뒤의
  `find.sh` 가 유일한 증거인 스냅숏을 덮어쓴 채 4~6번의 브랜치·원격 삭제까지 가고, 그러면 앞선 `remove` 가 엉뚱한
  것을 지웠어도 아무도 알 수 없다. 값을 스스로 짓지도 않는다 — 스냅숏 이름은 브랜치명에서 나오는데 이 시점엔
  브랜치를 아직 찾지 않았고(PR·이슈 번호에서 뒤에 찾는다), 대상 path 는 스냅숏 안에서 골라 주는 스크립트가 없고
  경로를 눈으로 고르지 않는다(문서 첫머리 규칙). 아직 아무것도 덮어쓰지 않았으니 값을 받으면 그때 확인하고 이어
  가면 된다.
- **`git worktree remove`·`lock`·`unlock` 에는 `--` 를 넣는다** — `git worktree remove -- "<인자>"`.
  이 절차는 밖에서 만든 워크트리도 대상으로 삼는데 그 이름에는 보장이 없어서, `-wip` 같은 이름이면
  따옴표를 붙여도 git이 `unknown switch` 로 끝난다(실측). (`git worktree add` 에는 넣지 않는다 —
  SKILL.md 생성 항목.)
- **워크트리를 가리키는 git 명령은 `path` 줄의 절대경로로 먼저 치고, `is not a working tree` 로 실패할
  때만 `suffix.sh` 가 준 접미사로 다시 친다.** 두 형태의 위험이 다르다.
  - git은 인자를 먼저 **등록 경로의 접미사**(`/` 경계, 대소문자 무시)로 맞춰 보고, 맞는 것이 **정확히
    하나가 아니면**(0개든 2개 이상이든) 인자를 **cwd 기준 경로로 다시 풀어 그 자리에 등록된 워크트리를
    잡는다** — exit 0이고 무엇을 잡았는지 알려주지 않는다(실측: `a/dup`·`b/dup` 이 등록된 상태에서
    `dup` 은 `a/` 안에서 `a/dup` 을, `b/` 안에서 `b/dup` 을 잡는다. 어느 접미사와도 안 맞는 `./dup`
    조차 `a/` 안에서 `a/dup` 을 잡았다). **잘못 짚은 접미사는 실패하는 대신 남의 워크트리를 지울 수
    있다.**
  - **절대경로에는 그 폴백이 없다.** `/` 로 시작하는 인자는 접미사 규칙상 완전 일치와 같고(실측 —
    등록된 `…/mirror/Users/me/target` 이 있어도 `/Users/me/target` 은 안 잡힌다 — 실측은 홈 디렉터리 아래 경로로 했다) cwd 와도 안
    합쳐진다. 맞으면 그 하나를 지우고, 어긋나면 **아무것도 안 하고** `is not a working tree` 다. 그래서
    기본형이고, 여기에는 유일성 확인을 걸지 않는다.
  - 절대경로가 어긋나는 원인은 **유니코드 정규화**다(심볼릭 링크 차이는 git이 realpath 로 흡수한다 —
    실측). 모델이 치는 경로는 NFC라 **NFD로 등록된 워크트리는 `path` 줄을 그대로 옮겨도 실패한다**
    (실측). SKILL.md 생성 항목대로 절대경로로 만든 워크트리는 NFC로 등록되지만, 본 체크아웃에 선 채
    상대경로로 `add` 한 워크트리가 NFD로 등록된 반례가 있다(실측). 밖에서 만든 워크트리·옛
    하네스가 남긴 잔재가 우회가 필요한 부류다.
  - 접미사는 **`suffix.sh` 가 낸 `SUFFIX` 줄만 쓴다.** 손으로 짓거나 눈으로 유일성을 세지 않는다.
- **`lock`·`unlock` 으로 대상을 시험하지 않는다.** 성공해도 무엇을 잡았는지 안 알려주고, 대상이
  잠겨 있었으면 `unlock` 은 출력 없이 exit 0으로 남의 잠금을 푼다(실측). 대상 확인은 `find.sh` 가 한다.
- **브랜치 이름을 `fetch`·`log`·`rev-parse`·`push --delete` 의 인자로 쓸 때는 `refs/heads/<브랜치>` 로
  적는다.** git 은 맨 이름을 `refs/tags/<이름>` → `refs/heads/<이름>` 순으로 풀어서, 같은 이름의 태그가
  있으면 브랜치가 아니라 태그를 잡는다(실측, git 2.50.1): `git fetch origin "<브랜치>"` 는 태그를 `FETCH_HEAD`
  로 받고 `refs/remotes/origin/<브랜치>` 를 **만들지 않으며**, `git fetch origin "<브랜치>:<브랜치>"` 는
  **태그 커밋을 가리키는 로컬 브랜치를 조용히 만든다.** `git log … "..<브랜치>"` 와 `merge-base` 는 태그
  커밋으로 계산하고, `git push origin --delete "<브랜치>"` 는 `dst refspec … matches more than one` 으로 죽는다.
  `refs/heads/` 를 붙이면 전부 브랜치로 간다. 지금 이 레포에는 태그가 없어 당장 터지지는 않지만,
  브랜치 이름이 이슈 번호에서 나와 사람이 고르지 않으므로 규칙으로 막아 둔다.
  **`git worktree add "<경로>" "<브랜치>"` 와 `git branch -D "<브랜치>"` 에는 붙이지 않는다** — 둘은 맨 이름을
  브랜치로 보고(실측), `worktree add` 에 `refs/heads/<브랜치>` 를 주면 오히려 **detached** 로 열린다(실측).
  `ls-remote --heads`·`for-each-ref refs/heads/…`·`gh pr list --head` 도 이미 브랜치만 본다. (같은 이름의
  태그가 있으면 `for-each-ref` 의 `%(refname:short)` 는 `heads/<브랜치>` 로 낸다 — 실측. 그래서 이 문서와
  merge-cleanup.md 의 `for-each-ref` 는 `%(refname)` 으로 전체 이름을 낸다.)
- **자기가 서 있는 워크트리는 안에 선 채 `remove` 한 뒤 `ExitWorktree(keep)` 로 나간다 — 순서를 바꾸지
  않는다.** 제거 절차 1번의 `INSIDE` 갈래가 이 순서다(전제·나간 뒤의 확인·실패 신호는 거기 있다). PR 을 만든
  세션에서 곧바로 "머지했어"를 받는 가장 흔한 흐름이 이 경우라, 그 세션에서 정리를 끝낼 수 있어야 한다.
  - **먼저 나가서 지우는 순서는 안 된다** — `ExitWorktree(keep)` 자체는 성공하지만 **바로 다음 Bash 명령이
    끝나면 하네스가 cwd 를 그 워크트리로 되돌리고 다시 격리한다.** 두 번째 `ExitWorktree` 는
    `No-op: there is no active EnterWorktree session to exit` 로 거부된다(머지 정리에서 실측). 세션이 시작된 디렉터리와는 무관하다 — 옛 문서는 이것을 "시작 위치가 마침 그 워크트리였던
    경우"로 잘못 진단했다.
  - **안에서 `remove` 한 뒤 나가는 순서는 머지 정리에서 여덟 번 통과했다.** `remove` 는 자기 cwd 를 지우고도 exit 0 으로 끝난다 — 셸 자체는 살아 있어 같은
    Bash 호출 안의 `echo` 같은 내장 명령은 돌지만(실측) **git 과 판정 스크립트는 못 돈다**(git 은 `Unable to
    read current working directory`, 스크립트는 `pwd -P` 가 실패해 `CWD_GONE`). 그래서 `remove` 와 사후 확인을
    `&&` 로 한 줄에 묶지 않는다. 격리는 남아 있어 `ExitWorktree(keep)` 가 받아 주고, **`EnterWorktree` 직전 cwd** 로
    돌려놓는다 — 그 "직전 cwd" 에는 Bash `cd` 로 바뀐 작업 디렉터리도 포함되므로 관측에서는 거의 매번 본
    체크아웃이었고 `git -C` 가 필요 없었다. 예외는 한 번이다 — `.claude/worktrees/` 아래의 git 에 등록되지 않은
    빈 폴더에서 `EnterWorktree` 한 세션은 그 폴더로 돌아갔다. 그 자리도 본 체크아웃 아래라 `same-repo.sh` 는
    `SAME_REPO` 였고 정리는 (e)까지 끝났지만, 그 뒤 다른 레포로 친 단독 `cd` 는 그 폴더로 되돌려졌다.
    그 뒤로는 Bash 마다 하네스가 `Shell cwd was reset to <그 경로>` 를 붙이지만 명령은 정상 실행된다(관측). 되돌리는 동작은 디렉터리가 남아 있을 때의 것이고
    지운 뒤에는 돌아갈 곳이 없어 나가기가 유지되는 것으로 보이지만, 어느 쪽도 도구 설명에 없는 하네스
    동작이다. 그래서 1번 갈래는 나간 직후 `same-repo.sh` 로 선 자리를 확인하고 어긋나면 멈춘다 — 하네스가
    바뀌면 거기서 잡힌다. `remove` 와 `ExitWorktree` 사이에는 Bash 를 치지 않는다(칠 것이 없다 — 사후
    확인은 나간 뒤에 한다). 쳤던 관측에서는 cwd 가 지워졌다는 안내와 함께 한 번 튕겼지만 격리는 남아
    `ExitWorktree` 가 그대로 받았다.
  `cd` 로 옮겨 다니지 않는다 — 세션의 작업 디렉터리는 하네스가 잡고 있어서 옮겼다고 믿고 친 명령이
  엉뚱한 곳에서 돈다. (격리되지 않은 세션이 요청의 처음에 이 스킬의 레포 밖에 서 있으면 본 체크아웃으로 옮기는
  것만 예외다 — 그 규칙은 SKILL.md "시작하기 전에" 한 곳에 있다.)
- **`git -C "<레포 루트>"` 로 돌리지 않는다.** 격리 세션에서는 하네스가 거부한다("this command
  redirects git to the shared checkout via `-C`" — 읽기 전용이라도, 실측). 격리가 풀린 세션에서는
  통과한다(실측). 그래도 쓰지 않는 이유는 **판정과 실행이 서로 다른 레포를 볼 수 있어서**다 —
  스크립트는 cwd 에서 판정하는데 비가역 명령만 `-C` 로 다른 곳을 치거나, 여러 명령 중 하나에서 `-C` 를
  빠뜨리면 그 명령이 남의 레포를 보고 판단한다. cwd 가 레포 밖이면 **멈추고, 본 체크아웃(`<레포 루트>`)
  안에서 레포 이름을 붙여 다시 불러 달라고 요청한다.**
- **사람에게 묻고 답을 받은 뒤에는 그 확인이 속한 번호의 처음부터 다시 돌고 이어 간다**(어디부터인지는 아래 2.가 정한다). 왕복은 몇 분에서 몇십
  분이고, 그 사이 다른 세션이 워크트리를 더하거나 지우거나 잠그거나, 사람이 브랜치를 바꾸거나 PR을 열 수
  있다. 낡은 출력으로 이어 가면 확인이 무의미해지고 사후 확인 기준선도 낡는다. 순서는 셋이다.
  1. **0번 ①(`same-repo.sh`)을 돌린다** — cwd 가 그 사이 레포 밖으로 나가지 않았는지 본다.
  2. **다음 비가역 명령을 지키는 확인을 모두 다시 돈다.** 어디서 물었느냐로 정한다.
     - **0~3번에서 물었으면 0번 ②부터 다시 돈다.** 다음 비가역 명령이 3번 `remove` 이고, 그것을 지키는 열린
       PR(②)·대상 특정(③)·잠금과 detached(④)가 왕복 중에 바뀌었을 수 있다. ③이 스냅숏을 새로 뜨므로 3번
       사후 확인의 기준선도 낡지 않는다. **2번(도는 작업 멈추기)에서 사람에게 물었어도 여기 해당한다** — 2번만
       다시 돌고 3번으로 가면, 그 사이 누가 bisect 를 시작해 detached 가 된 워크트리를 낡은 대상 그대로 지운다.
     - **4~6번에서 물었으면 그 번호의 처음부터 다시 돈다** — 4번은 그 경로의 1)부터, 5번은 ①부터, 6번은
       열린 PR 확인부터. 대상 워크트리는 3번에서 이미 지워졌고, 4번 `rm -rf`·5번 `branch -D`·6번
       `push --delete` 는 각자 그 번호 안의 확인들에 기댄다. 질문을 낸 확인 하나만 다시 돌면 같은 번호의 다른
       방벽을 건너뛴다 — 5번 ②에서 묻고 기다리는 사이 누가 그 브랜치 커밋에서 bisect 를 시작하면, ①(detached)을
       안 보고 `branch -D` 가 돈다. 0번으로는 되돌아가지 않는다 — 되돌아가면 앞 번호를 다시 지나 같은 질문에
       닿아 정리가 끝나지 않는다. 4번 안에서 2번을 불러 사람에게 물었으면 4번의 질문으로 친다.
  3. **다시 돈 출력이 답할 때 보여 준 것과 같으면 다시 묻지 않고 그 답대로 간다.** 하나라도 다르면 그 사이
     상태가 바뀐 것이니 새 출력을 보여 주고 새로 묻는다.
- **답과 승인은 그때 보여 준 출력에 붙는다.** 위 3.의 "같은가"를 0번 ③에서는 이렇게 본다:
  - **특정 레코드를 지목한 답**이면 셋째 인자로 그 `path` 를 준다 — 이름으로 다시 찾으면 왕복 중에 같은
    이름이 하나 더 등록됐을 때 엉뚱한 줄을 집는다. 다시 돈 ③이 `FOUND` 이고 그 블록이 답할 때 본 그 레코드의
    블록과 같으면 ④로 간다. ④의 `detached`·`container out` 은 **그 사실을 보여 주고 받은 답**일 때만 그
    답으로 통과한다.
  - **"보여 준 것 중 지울 워크트리가 없다"는 답**(`AMBIGUOUS` 에 "아무것도 아니다", `MISMATCH` 에 "이
    브랜치 정리를 이어 가라", `DETACHED_CANDIDATES` 에 "쥔 것이 없다")이면 셋째 인자 없이 부른다. 첫 줄과
    블록들이 답할 때 본 것과 같으면 `NONE` 과 같이 1~3번을 건너뛰고 4번으로 간다.
  - 블록끼리 견주는 줄은 `path`(또는 `path-escaped`)·`branch`(또는 `branch-escaped`·`detached`)·`locked`·`container`·`unsafe`·
    `dangling`·`unreadable`·`prunable` 이다(`prunable` 이 사라졌으면 그 사이 디렉터리가 돌아온 것이다 —
    외장 볼륨을 다시 붙였거나 누가 그 자리에 다시 썼다. 승인은 그 상태에 붙은 게 아니니 새로 묻는다).
    **`detached` 를 보여 주고 받은 승인은 `head` 줄까지 견준다** — 승인과
    `remove` 사이에 누가 그 워크트리에서 커밋하면 트리가 깨끗해 `remove` 가 그대로 지우고, 그 커밋은 어느
    브랜치에도 없어 reflog 에만 남는다. `record` 번호와 `match` 줄은 부르는 방법에 따라 달라지므로 보지 않는다.
  다른 자리에서는 그 확인이 낸 것을 통째로 견준다 — 스크립트 출력, `git log` 커밋 목록, `gh pr list` 의 PR
  번호, `prune --dry-run` 목록. **여러 줄 중 하나를 고른 답은 삭제 승인이 아니다** — 고른 줄이 detached
  이거나 레포 밖이면 그 사실을 보여 주고 따로 묻는다. `locked` 는 어떤 답으로도 통과하지 않는다(사람이 풀어야
  한다). **승인은 그 등록에만 붙는다** — 3번이 대상을 지운 뒤(사후 확인 `REMOVED`) 같은 경로에 다시 생긴
  등록은 블록이 바이트까지 같아도 다른 워크트리라, 이전 답과 승인을 그것에 쓰지 않는다(4번 1)의
  `REGISTERED`).
- 명령 가드는 명령의 **형태**만 볼 뿐 대상은 보지 않는다 — **인자를 잘못 짚으면 절대경로든 접미사든
  그대로 지워진다.**

## 잔재 조사 — 2단계에서 `RESIDUE` 가 나왔을 때

**자동으로 처리하지 않는다 — 상태를 모아 보여주고 묻는다.** 잔재는 자주 나오지 않고, 잘못 판단하면
되돌릴 수 없다(워크트리·브랜치·원격 삭제). 상태를 자동으로 분류하려던 판이 실제로 여러 번 틀렸고,
틀리는 방향이 매번 파괴 쪽이었다 — 살아 있는 워크트리를 고아로, 살아 있는 브랜치를 빈 껍데기로 읽어
지우는 쪽. 사람은 같은 화면을 1초에 읽는다. 왕복 한 번이 그보다 싸다.

**아래 출력을 해석 없이 그대로 보여준다.** `residue.sh` 가 낸 `branch` 줄마다 뒤의 두 명령을 한 번씩
돌린다 — 재시도 슬러그로 브랜치가 둘이면 둘 다 보여줘야 사람이 고른다. `branch` 줄이 없고 디렉터리만
있으면 그 둘은 건너뛴다. **`branch-escaped` 줄은 그 둘에 옮기지 않는다** — 명령에 넣을 수 없는 브랜치
이름이다(SKILL.md "인자는 큰따옴표로 감싼다"). 그 줄을 그대로 보여 주고, 이 스킬이 만든 이름이 아니라는 것을
함께 적는다. 사람이 그 브랜치를 이어받으라고 하든 버리라고 하든 이 워크플로는 다루지 않는다(위 "먼저 알아 둘
것"). **`branch-escaped` 줄 말고는 이 이슈의 잔재가 없으면** 그 사실을 함께 보여 주고 묻는다 — 사람이 그 브랜치는
이 이슈와 무관하니 두고 진행하라고 하면 SKILL.md 2단계의 생성으로 간다(새로 지을 이름은 영어 슬러그라 그 이름과
겹치지 않는다). 그 줄은 최종 보고에 남긴다.

```
bash "<스킬 디렉터리>/scripts/residue.sh" <이슈번호>
git worktree list --porcelain
git for-each-ref --format='%(refname) %(objectname) %(worktreepath)' "refs/heads/<브랜치>" "refs/remotes/origin/<브랜치>"
gh pr list --head "<브랜치>" --state all --limit 100 --json number,state,baseRefName,headRefOid
```

**출력을 옮길 때 알아야 할 것**(읽는 법이지 판단 근거가 아니다):
- `gh pr list --head` 는 이미 머지·삭제된 브랜치의 이름도 **영원히** 매칭한다. 여러 건이 나오는 게
  정상이니 **하나로 줄이지 말고 다 보여준다** — 어느 것이 지금 상태를 대표하는지 고르려던 시도가
  반복해서 틀렸다(`mergedAt` 로 고르면 MERGED가 OPEN을 항상 이기고, `number` 로 고르면 나중에 닫힌 PR이
  머지된 PR을 가린다 — 둘 다 실측). **`--limit 100` 을 빼지 않는다** — 기본값은 **30**이라(실측)
  잘리면 제거 절차의 열린 PR 확인이 첫 페이지 밖의 PR을 못 보고 원격 브랜치를 지워 **GitHub이 그 PR을
  닫는다.** 이 절차의 `gh pr list` 는 전부 같은 이유로 `--limit` 를 단다. **`baseRefName` 도 같이
  보여준다** — `main` 이 아닌 base의 PR(이 레포는 `main` 하나로 운영하지만 사람이 다른 base 로 열 수 있다)이 섞일 수 있고, 모르고 이어받으면 5단계 push가
  그 PR에 이번 작업을 얹는다.
- `for-each-ref` 가 내는 **로컬 팁을 L, 원격 팁을 R** 이라 부른다(없으면 "없음"). **`%(objectname)` 이라 전체
  40자 sha 다** — 6번이 `ls-remote` 가 낸 sha 와 그대로 견주므로 축약형(`%(objectname:short)`)을 쓰면 늘
  "다르다"가 되어 원격 정리가 끝나지 않는다(이전 리뷰에서 잡힌 실제 결함이다). 이어받기 4번과 제거
  절차 5·6번이 이 이름을 쓴다. 줄은 `전체 ref 이름 SHA [워크트리 경로]` 다 — 로컬 줄은 `refs/heads/<브랜치>`, 원격
  줄은 `refs/remotes/origin/<브랜치>` 로 시작하고 원격 줄에는 경로 칸이 없다. 같은 이름의 태그가 있어도 이름이 바뀌지
  않는다(`%(refname:short)` 는 그때 로컬 줄을 `heads/<브랜치>` 로 낸다 — 위 "먼저 알아 둘 것"). **줄이
  셋 이상이면 이름을 확인한다** — git은 "완전히 같거나 슬래시 앞까지 같으면" 매칭하므로 `fix/278` 을
  물으면 `refs/heads/fix/278/sub` 도 나온다. L 은 이름이 정확히 `refs/heads/<브랜치>` 인 줄, R 은 정확히
  `refs/remotes/origin/<브랜치>` 인 줄이다. **없는 ref는 조용히 생략한다**(실측) — 출력이 비면 정말 ref가 없다.
  (`%(ahead-behind:…)` 를 쓰지 않는다 — git 2.41 미만에서는 명령 전체가 죽어 빈 출력이 "ref 없음"과
  구분되지 않는다.)
- `%(worktreepath)` 는 **브랜치가 체크아웃된 워크트리에만** 붙는다 — 사람이 그 안에서
  `git checkout <sha>` 로 bisect 중이면(detached HEAD) 비어 있다. 그래서 porcelain을 같이 낸다.
  porcelain은 **첫 레코드가 본 체크아웃**이고 레코드마다 `branch`(detached면 없음)·`locked`·`prunable`
  이 붙을 수 있다.
- `residue.sh` 의 `worktree` 줄은 이 이슈 이름으로 등록된 워크트리다 — `.claude/worktrees/` 밖에 등록된
  것, 디렉터리가 지워지고 등록만 남은 것(porcelain 에 `prunable` 이 붙는다)도 여기 나온다. 경로는 **등록된
  바이트 그대로**라 `find.sh` 의 `path` 줄과 같다. `orphan`·
  `other-orphan` 줄은 `.claude/worktrees/` 아래 디렉터리 중 등록된 어느 경로와도 **같은 디렉터리(-ef)가 아닌**
  것이다 — 이름으로 맞춘 게 아니라서 레포 밖의 같은 이름에 속지 않는다.
- `link` 줄은 `.claude/worktrees/` 안의 **심볼릭 링크**로, 이 이슈 이름이고 등록된 워크트리를 가리킨다.
  바로 뒤 `link-target` 줄이 가리키는 등록 경로다. 그 등록이 이 이슈 이름이면 `worktree` 줄에도 나오고,
  **다른 이슈의 워크트리나 본 체크아웃이면 `worktree` 줄에는 나오지 않는다** — 링크 이름만으로 남의 등록을
  이 이슈 잔재로 올리면, 사람이 화면대로 그 브랜치 이름을 답했을 때 정리 절차가 남의 워크트리·브랜치를
  지운다. **링크 자체는 이 절차가 지우지 않는다** — 링크 경로에 `git worktree remove` 를 치면 링크는 남고
  **가리키는 워크트리가 지워지며**(rc 0, 실측), `rm -rf` 는 끝에 `/` 가 붙으면 가리키는 디렉터리를 비운다
  (실측). 4번의 `orphan-check.sh` 도 링크 경로를 `REGISTERED` 로 판정해 멈춘다. 보고에 적고, 사람이
  `rm "<링크>"` 로 치운다. `link` 줄만 있고 `branch`·`worktree` 줄이 없으면 이 이슈의 잔재는 그 링크뿐이다 —
  사람이 치운 뒤 SKILL.md 2단계의 생성으로 간다.

**그다음 묻는다.** 답을 받으면 아래 "이어받기" 또는 "잔재 정리"를 그대로 실행한다. 답이 없으면 진행하지
않는다. 잔재가 여러 개면 각각 어떻게 할지 받는다 — 하나만 처리하고 나머지를 조용히 남기지 않는다.
**다른 이슈의 잔재(`other-orphan`)는 건드리지 않고 존재만 보고한다.**

**답과 무관하게 지키는 것 셋:**
- **`locked` 이 붙은 워크트리는 우리가 풀지 않는다.** SKILL.md 생성 항목대로 만든 워크트리는 잠기지
  않으므로, 잠금이 있다는 건 다른 하네스 세션이 쓰고 있거나(`EnterWorktree(name:)` 이 세션 pid로 건다 —
  이 워크플로의 옛 버전도 그랬다) 사람이 일부러 건 것이다. `unlock` 도 `remove -f -f` 도 하지 않는다 —
  사람이 풀어 주면 그때 진행한다. 옛 버전이 만든 잠금은 그 세션이 끝나면 풀린다(실측).
- **본 체크아웃이 그 브랜치를 쥐고 있으면(`find.sh` 가 `MAIN_HOLDS`) 아무것도 하지 않는다.** 사람이
  테스트하려고 `git checkout` 해 둔 것이다 — 들어갈 수도 지울 수도 없으니 `git switch main` 을 요청한다.
- **`.claude/worktrees/` 밖에 등록된 워크트리(`container out`)는 이어받기가 조건부다** —
  `EnterWorktree(path:)` 는 **이미 격리된 세션**에서는 그 아래로만 전환하지만, 시작 디렉터리에서 처음
  들어갈 때는 `git worktree list` 에 있기만 하면 된다(도구 설명). 격리 상태면 이어받지 못하니 그 사실을
  알리고, 격리되지 않았으면 시도해 본다 — 거부되면 그때 보고한다. 제거는 진입이 필요 없으므로 어느
  경우든 사람이 지우라고 하면 할 수 있다.

## 이어받기 — 사람이 이어받으라고 했을 때

순서가 중요하다 — **들어간 것을 확인한 뒤에야** 브랜치를 손댄다.

1. **워크트리를 찾는다:**

   ```
   bash "<스킬 디렉터리>/scripts/find.sh" "<스냅숏>" "<브랜치>"
   ```

   - `FOUND` — 블록을 본다. `unsafe yes`·`locked`·`unreadable yes` 면 멈추고 보고한다. `dangling yes` 면
     브랜치 ref 가 지워진 등록이라 그대로는 이어받을 수 없다 — **`prunable` 이 함께 있으면**(디렉터리도
     없다) 아래 `prunable` 갈래로 그 등록을 치우고 재부착하고(로컬 ref 가 없으니 재부착 전에
     `git fetch origin "refs/heads/<브랜치>:refs/heads/<브랜치>"` 로 받는다), 디렉터리가 남아 있으면 3번
     `remove` 가 거부하므로 멈추고 보고한다.
     **`detached` 면 멈추고
     보고한다** — 누군가 그 안에서 bisect 중일 수 있고, 거기에 이어 커밋할 수 없다.
     **`prunable` 이면 들어가지 않고 등록부터 치운다** — 디렉터리가 사라졌거나 `.git` 없이 되살아난
     등록이라, 들어가도 git 이 본 체크아웃을 봐서 2번에서 "진입 실패"로 멈춘다. 아래 제거 절차를
     **0번 ①·③·④와 1~3번만** 돌려 그 등록을 치우고, 끝나면 `NONE` 갈래의 재부착으로 간다.
     - **0번 ②(열린 PR)는 건너뛴다** — 이어받는 브랜치는 PR 이 열려 있는 게 정상이고(6단계 재진입이
       늘 그렇다), 이 호출은 브랜치도 원격도 건드리지 않는다. 사람 답을 받아 다시 돌 때("먼저 알아 둘
       것")도 ②는 건너뛰고 ③부터 돈다.
     - 4~6번은 돌지 않는다. 되살아난 디렉터리가 남으면 재부착의 `already exists` 갈래가 그 경로로 4번을
       부른다.
     - 번호를 골라 들어오므로 제거 절차 앞머리(사본 뜨기)를 안 지난다 — 그 번호들의 `<사본>/scripts/…` 는
       `<스킬 디렉터리>/scripts/…` 로 읽는다(등록만 치우는 경로라 스킬 디렉터리가 사라질 일이 없다). 이 세션이
       앞서 제거 절차를 지나 `<사본>` 이 이미 있으면 그것을 써도 같다.

     그 밖이면 `git branch --show-current` 로 **이미 그 안에 서 있는지** 본다(사람이 그 디렉터리에서 터미널을
     열고 `/issue <번호>` 를 돌린 경우로, 자연스러운 재개 방식이다). 서 있지 않으면 `path` 줄로
     **EnterWorktree(path:)** 한다. `container out` 이면 위 "답과 무관하게 지키는 것"대로 한다.
   - `MAIN_HOLDS` — 멈추고 `git switch main` 을 요청한다.
   - `MISMATCH`·`AMBIGUOUS`·`DETACHED_CANDIDATES` — **멈추고 블록을 보여주고 묻는다.** 특히 detached
     후보 중 하나가 이 브랜치를 쥐고 있을 수 있다 — 그대로 재부착하면 `already exists` 로 실패하고, 그걸
     고아로 오진하면 사람이 쓰는 체크아웃을 지운다.
   - `NONE` — 등록이 정말 없다(제거·prune 뒤 브랜치·PR만 남은 복구 상태). **재부착**한다:
     `git worktree add "<레포 루트>/.claude/worktrees/<평탄화한 브랜치명>" "<브랜치명>"` 뒤
     EnterWorktree(path:)로 진입한다. 원격에만 있던 브랜치면 먼저
     `git fetch origin "refs/heads/<브랜치>:refs/heads/<브랜치>"` 로 로컬에 받는다 — 양쪽 다 `refs/heads/` 를
     붙인다("먼저 알아 둘 것": 맨 이름이면 같은 이름의 태그가 있을 때 태그 커밋을 가리키는 로컬 브랜치가
     생긴다). `worktree add` 쪽 `<브랜치명>` 에는 붙이지 않는다(같은 항목 — 붙이면 detached 로 열린다).
     **`already exists` 로 실패하면** 그 자리에 등록 없는 디렉터리가 있는 것이다(지운 뒤 Finder 가
     `.DS_Store` 를 다시 썼거나 JetBrains IDE(PyCharm 등)·도는 프로세스가 그 경로에 파일을 썼다 — 빈 디렉터리가 아니면
     `add` 가 거부한다). 아래 제거 절차 **4번만** 돌리되 **대상은 방금
     `add` 가 실패한 그 경로 하나로 못박는다** — 이슈 번호로 훑는 갈래로 흘려보내면 재시도 슬러그
     (`fix+287-a`·`fix+287-b`)가 둘 다 걸려 막고 있지 않은 쪽까지 지운다. 처리한 뒤 재부착을 다시
     시도한다.
2. `git branch --show-current` 가 그 브랜치인지 **확인한다.** 아니면 진입이 실패한
   것이니 멈추고 보고한다 — 아래 단계를 엉뚱한 브랜치(`main` 포함)에 적용하게 된다.
3. **`git status --porcelain` 이 비어 있는지 본다.** 비어 있지 않으면 **다른 세션이
   지금 그 워크트리에서 작업 중이거나 커밋 전에 중단된 편집**이다 — 이 워크플로는
   잠금을 쓰지 않으므로 이 확인이 "남이 쓰는 중"을 가리는 유일한 신호다. 멈추고
   묻는다. 그대로 가면 3단계가 파일 단위로 커밋하면서 남의 반쯤 된 편집을 자기
   커밋에 쓸어 담아 그 PR에 push한다.
4. **원격이 앞서 있으면 따라잡는다** — R이 있고 L ≠ R 이면
   `git merge --ff-only "origin/<브랜치>"`. 다른 머신의 push나 GitHub의 리뷰 제안
   적용이 이 모양을 만든다. ff가 안 되면(양쪽에 다른 커밋) **묻는다** — 그대로 가면
   3단계 커밋이 낡은 팁에 쌓이고 5단계 push가 non-fast-forward로 거부되는데,
   거기엔 거부를 다루는 갈래가 없다. **이 명령을 2번 전에 돌리면 안 된다** — 아직
   `main` 에 서 있으면 `main` 이 기능 브랜치의 조상이라 ff가 **성공**해 버리고,
   로컬 `main` 이 기능 브랜치를 가리키게 된다.
5. **upstream이 있으면 무조건 뗀다** — `git branch --unset-upstream || true`.
   **`|| true` 를 떼지 말 것.** upstream이 없으면 이 명령은
   `fatal: branch '<이름>' has no upstream information` 으로 **exit 128** 이다(실측).
   그런데 upstream이 없는 것이 흔한 정상 상태다 — 이 워크플로가 `--no-track` 으로
   만든 브랜치가 5단계 `push -u` 전에 중단되면 그 모양이다. 가리지 않으면 실패에
   민감한 실행이 리뷰·push 전에 여기서 멈춘다. 값이 무엇이든 떼는 이유가 둘이다:
   - `origin/main` 이면(이 워크플로의 옛 버전이 만든 브랜치가 그 상태다 — 실측)
     5단계 전에 멈췄을 때 사람이 맨 `git pull` 을 쳐서 `origin/main` 이 작업
     브랜치에 머지되고 그 커밋이 PR에 들어간다.
   - `origin/<브랜치>` 면(이전 실행이 5단계 `push -u` 까지 갔다 중단된 경우)
     4단계에서 `/code-review` 가 범위 지정을 놓치고 기본 갈래로 떨어졌을 때
     `@{upstream}...HEAD` 가 **빈 diff**가 되어(방금 4번에서 ff로 따라잡았으므로)
     리뷰가 아무것도 안 보고 P1·P2 0건으로 게이트를 통과한다. 5단계가 다시
     `push -u` 로 걸어 주므로 여기서 떼도 잃는 게 없다.
6. **브랜치 이름은 이미 있는 것을 그대로 쓴다.** 규약 형태(`<타입>/<번호>-<슬러그>`)
   에 맞으면 슬러그가 이번에 지었을 것과 달라도 바꾸지 않는다 — 바꾸면 5단계
   `push -u` 가 두 번째 원격 브랜치를 만들고, 그 뒤로 모든 세션의 잔재 조사에 브랜치가 둘로 나온다.
   **규약 밖 이름**(`worktree-fix+278-…` 처럼 옛 경로로 만들어진
   것)만 `git branch -m "<타입>/<이슈번호>-<슬러그>"` 로 되돌린다 — `residue.sh` 판별식이 그런 이름까지
   잡는 이유다. 단, **그 옛 이름이 이미 push됐거나
   (R 있음) 그 이름으로 PR이 있으면 개명하지 않는다** — `gh pr edit` 는 head
   브랜치를 못 바꾸므로 개명하면 PR이 둘로 갈라진다. 그 경우 옛 이름 그대로
   진행하고 보고에 남긴다.

## 잔재 정리 — 사람이 버리라고 했을 때

**아래 "워크트리 제거 절차"를 그대로** 따른다. 대상 브랜치는 `residue.sh` 의 `branch` 줄에서 온다 —
`branch` 줄 없이 `worktree` 줄만 있으면 제거 절차 앞머리대로 브랜치 이름부터 받는다. 그렇게 받은 이름이 명령에
넣을 수 없는 이름이면 멈추고, 남은 `worktree` 줄의 경로를 보고에 적는다(그 등록은 다음 `/issue` 의
`git worktree add` 를 막는다). `branch-escaped` 줄의 브랜치는 버리라는 답이어도 이 절차로 지우지 않는다(위 "먼저
알아 둘 것") — 그 사실을 보고하고 사람이 치우게 한다. 브랜치 없이 고아
디렉터리만 정리하라는 답이면 절차의 **4번만** 돌리고, 대상은 `residue.sh` 가 낸 그 `orphan` 줄의 경로다.
정리가 끝나야 SKILL.md 2단계의 생성으로 진행한다. 생성이 `already exists` 류로 실패하면 위 "잔재 조사"로
돌아가 다시 보여주고 묻는다. **현재 이슈와 무관한 잔재**(다른 이슈 번호의 브랜치·워크트리, 유래를 모르는
디렉터리)는 건드리지 않는다.

## 워크트리 제거 절차

2단계 잔재 정리와 7단계 (b)~(d)가 **똑같이** 쓴다. 대상은 브랜치 이름 하나다. **0번부터 순서대로**
돈다 — 앞 번호가 뒤 번호가 쓸 대상을 정한다.

**브랜치 이름이 없으면 먼저 받는다.** `residue.sh` 가 `branch` 줄 없이 `worktree` 줄만 낸 경우다 — 브랜치
ref 는 지워졌는데 등록이 남았다(그대로 두면 같은 슬러그의 `git worktree add` 가 `missing but already
registered` 로 막힌다). 그 줄과, `git worktree list --porcelain` 의 그 레코드에 남은 `branch` 줄(ref 를 지워도
남는다 — 실측)을 보여 주고 **어느 브랜치의 워크트리인지 묻는다.** 디렉터리 이름에서 브랜치 이름을 추측하지
않는다. 이름을 받으면 먼저 잔재 조사의 `git for-each-ref` 한 줄로 **L·R 을 받아 둔다** — 5번 ②와 6번이
"R 이 있으면"으로 쓰는데, 잔재 조사는 `branch` 줄마다만 그 명령을 돌려서 이 경우엔 값이 없다(7단계에서 왔으면
merge-cleanup.md 가 이미 받는다). 그다음 그 이름으로 0번부터 돈다.

**받은 이름이 그 등록의 것인지는 0번 ③이 가리는데, 통과 조건을 못박는다.** ③을 **셋째 인자로 그 `worktree`
줄의 경로를 주어** 부르고, 첫 줄이 `FOUND` 이고 블록에 **`branch refs/heads/<받은 이름>` 줄이 있을 때만** 이어
간다. 경로가 같은지는 스크립트가 정규화해서 가린다 — `residue.sh` 의 `worktree` 줄과 `find.sh` 의 `path` 줄은
둘 다 등록된 바이트를 내지만 사람이 옮겨 치는 사이 표기(NFC/NFD)가 바뀔 수 있고, 한글은 터미널에서 눈으로
구분되지 않는다(문서 첫머리 규칙).
`GONE` 이면 그 경로의 등록이 사라진 것이고 `MISMATCH` 면 그 등록이 쥔 브랜치가 받은 이름과 다르다 — 어느
쪽이든 멈추고 그 출력을 보여 주고 다시 묻는다. 이름 조각만 맞아 `match name` 으로 잡힌 detached 등록을
통과시키면 사람이 추측한 이름으로 5·6번(로컬·원격 브랜치 삭제)이 돈다. 그대로 흘려보내면 1~3번을 건너뛴 채 5번 `branch -D` 가
**그 이름의 다른 브랜치**를 지운다(이전 교차 리뷰에서 실측). 그리고 `branch` 줄 없이 `worktree` 줄만
나오는 모양은 ref 가 지워진 경우만이 아니다 — 그 워크트리 안에서 **다른 이슈 브랜치로 `switch` 한 살아 있는
등록**도 같게 보인다. 그래서 물을 때 "이 이름으로 5·6번(로컬·원격 브랜치 삭제)까지 돈다"는 것도 함께 적는다.

**0번에 들어가기 전에 스크립트·references·SKILL.md 를 레포 밖으로 복사해 둔다** — cwd 가 어디든, 대상이 무엇이든 한다.
`<스킬 디렉터리>` 는 `/issue` 를 부른 시점의 위치로 잡혀 cwd 와 무관하게 지울 워크트리 안일 수 있고(머지 정리에서
실측 — 본 체크아웃의 `main` 은 (e)에서야 당겨지므로 그쪽 사본은 낡았거나 없을 수 있다), 그러면 3번 `remove` 가
스크립트와 이 문서까지 지워 사후 확인과 4~6번이 부를 것도 다시 읽을 것도 없다. 어디를 가리키는지는 따지지
않는다 — 경로를 눈으로 견주지 않는다는 문서 첫머리 규칙 그대로다:

```
mktemp -d /tmp/issue-scripts.XXXXXX
cp -R "<스킬 디렉터리>/scripts" "<스킬 디렉터리>/references" "<스킬 디렉터리>/SKILL.md" "<mktemp 가 낸 경로>/"
```

둘 다 격리 세션의 명령 가드를 통과한다(실측). `mktemp` 가 낸 경로를 아래에서 `<사본>` 이라 부른다. **이 세션에서
그 뒤에 부르는 스크립트는 전부 사본으로 친다** — 이 절차 0~6번은 경로를 `<사본>/scripts/…` 로 적어 두었고, 2단계
잔재 정리로 왔다면 그 뒤 새 워크트리에서 도는 6단계 재진입의 `find.sh` 까지다. 다른 문서에
`<스킬 디렉터리>/scripts/<이름>.sh` 라고 적힌 자리도 이 뒤로는 `<사본>/scripts/<이름>.sh` 로 읽는다. **이 문서와
merge-cleanup.md 를 다시 Read 할 때도 `<사본>/references/<이름>.md` 로, SKILL.md 는 `<사본>/SKILL.md` 로 읽는다** —
3번 `remove` 뒤에는 원본이 없을 수 있다((e)가 SKILL.md 2단계 항목을 정본으로 가리킨다). 사본은 지우지 않는다(임시
디렉터리라 OS 가 치운다). 사람 답을 받아 0번부터 다시 돌 때 또 뜨지 않아도 된다 — 같은 세션이면 먼저 뜬 사본이
그대로 있다.

### 0. 대상 특정

① **cwd 가 이 레포 안인지 본다** — 이 절차의 모든 git 명령과 스크립트가 여기 달려 있다:

```
bash "<사본>/scripts/same-repo.sh" "<레포 루트>"
```

`SAME_REPO` 가 아니면(`OTHER_REPO`·`NOT_IN_REPO`·`CWD_GONE`) **멈추고, 본 체크아웃(`<레포 루트>`) 안에서
레포 이름을 붙여 다시 불러 달라고 요청한다.** 레포 밖에서 시작한 세션은 SKILL.md "시작하기 전에"가 먼저 옮기므로, 여기 오는 것은
그 뒤에 작업 디렉터리가 바뀐 경우다. `git -C` 로 우회하지 않는다(위 "먼저 알아 둘 것"). 이 확인이 잡는 것은 "cwd 가 레포 밖에
있는가" 하나다 — `<레포 루트>` 를 같은 cwd 에서 구했으므로 처음부터 다른 레포에서 시작한 세션은
통과한다. 그 레포에도 같은 번호의 브랜치·워크트리가 있을 수 있어(`/issue` 사본이 있는 다른 레포도 같은 이름 규약을 쓴다) ③이
남의 레포 것을 `FOUND` 로 잡는다. 그것을 막는 것은 SKILL.md "시작하기 전에"다.

② **그 브랜치로 열린 PR이 있으면 절차 전체를 멈추고 그 번호를 짚어 다시 묻는다:**

```
gh pr list --head "<브랜치>" --state open --limit 100 --json number
```

6번에도 같은 확인이 있지만 거기서는 늦다 — 1~5번이 이미 워크트리와 로컬 브랜치를 지운 뒤다. 잔재
조사는 `--state all` 로 여러 건을 보여 주므로 사람이 MERGED 여러 줄 사이의 OPEN 한 줄을 못 보고
"버려"라고 답할 수 있고, 7단계로 바로 들어온 세션은 그 조사를 안 봤다. 7단계 (a)를 통과했으면 그 PR은
MERGED라 여기 안 걸린다 — 걸린다면 지우려는 브랜치와 머지된 PR이 어긋난 것이니 멈추는 게 맞다.

③ **레코드를 찾는다:**

```
bash "<사본>/scripts/find.sh" "<스냅숏>" "<브랜치>"
```

평탄화한 브랜치명(이름)과 `branch` 줄로 함께 찾아 하나로 좁혀지는지 본다. 규약 밖 이름이 브랜치를
쥔 워크트리(사람이 만든 `exp-302-trial` 같은)도 `branch` 줄로 잡힌다. 사람이 고른 레코드로
다시 돌 때는 셋째 인자로 그 `path` 를 준다.

| 첫 줄 | 뜻 | 할 일 |
|---|---|---|
| `MAIN_HOLDS` | 본 체크아웃이 그 브랜치를 쥐고 있다 | 아무것도 하지 않고 `git switch main` 을 요청한다. 그대로 가면 3번이 `is a main working tree` 로 실패한다 |
| `FOUND` | 대상이 하나다 | ④로 |
| `MISMATCH` | 이름·경로는 맞는데 다른 브랜치를 쥐고 있다(사람이 그 안에서 `git switch` 했다). 블록에 `unreadable yes` 가 있으면 `switch` 가 아니라 HEAD 를 못 읽는 깨진 등록이다 | 블록을 보여준다. **이 절차는 그 워크트리를 지우지 않는다** — 이 브랜치의 워크트리가 아니고, 지우면 무관한 워크트리를 지운 채 5·6번이 이 브랜치의 원격까지 지운다(그 워크트리를 치우려면 그것이 쥔 브랜치 이름으로 이 절차를 따로 돈다). 묻는 것은 이 브랜치의 정리를 이어 갈지다 — 이어 가라는 답이면 위 "답과 승인은 그때 보여 준 출력에 붙는다"대로 `NONE` 과 같이 간다 |
| `AMBIGUOUS` | 후보가 둘 이상이다 — 레포 밖에 같은 이름이 있거나, 이름 후보와 branch 후보가 다르거나, 같은 디렉터리에 표기(NFC/NFD)만 다른 쌍둥이 등록이 있다(`match same-dir`) | 블록을 보여주고 어느 것인지, 또는 아무것도 아닌지 묻는다. 지목하면 그 `path` 를 셋째 인자로, 아무것도 아니라면 `NONE` 과 같이 간다(위 "답과 승인은 그때 보여 준 출력에 붙는다"). **`match same-dir` 블록이 있으면 이 절차로는 가를 수 없다** — 어느 줄을 지목해도 절대경로 `remove` 는 모델이 친 NFC 바이트와 같은 쪽을 지우므로, 멈추고 사람에게 넘긴다 |
| `DETACHED_CANDIDATES` | 못 찾았는데, origin/main 에 없는 커밋에 선 detached 연결 워크트리가 있다(origin/main 에 이미 있는 커밋에 선 것은 스크립트가 뺀다) | 블록을 보여주고 **두 가지를 함께 묻는다** — 그중 이 브랜치를 쥔 것이 있는지, 있으면 지워도 되는지(detached 라 누군가 bisect 중일 수 있다). "없다"는 답이면 `NONE` 과 같다. **`match detached-unresolved`** 는 그 HEAD 가 가리키는 커밋을 git 이 못 찾는다는 뜻이다(force-push 뒤 gc) — 정체를 가릴 수 없고, 지우라는 답을 받아도 3번 `remove` 가 `bad object HEAD` 로 실패하니 그 사실을 함께 보여준다 |
| `NONE` | 등록된 워크트리가 없다 | 1~3번을 건너뛰고 4번으로 |
| `GONE` | (셋째 인자로 부른 경우) 그 경로의 레코드가 없다 | 그 사이 사라졌다. 셋째 인자 없이 ③을 다시 돈다 |
| `MAIN` | (셋째 인자로 부른 경우) 그 경로가 본 체크아웃이다 | 멈추고 보고한다 |

④ **대상 블록을 본다** — 위에서부터, 걸리면 거기서 멈춘다:
- `unsafe yes` — 경로에 셸이 건드리는 문자가 있다: 큰따옴표 안에서 먼저 확장되는 `$`·백틱·`"`·`\`,
  작은따옴표 `'`, 그리고 개행·제어 문자. **치지 말고 사람에게 넘긴다** — `/tmp/wip-$USER-old` 같은 등록은
  큰따옴표 안에서 다른 경로가 되어, 운이 나쁘면 그 자리의 다른 워크트리가 지워진다. (`'` 를 거르는 것은 경로를
  작은따옴표 안에 넣는 명령(`osascript -e '…'` 같은)을 깨기 때문이다. 이 레포 명령은 깨지 않지만 판정 스크립트를
  다른 사본과 같게 두려고 그대로 거른다.)
- `unreadable yes` — HEAD 를 못 읽는 깨진 등록이다. HEAD 가 0바이트면 `branch` 줄도 `detached` 줄도 없고,
  HEAD 파일이 아예 없으면 `detached` 가 함께 붙는다(실측). 어느 쪽이든 어느 브랜치를 쥐었는지도 누가 쓰는
  중인지도 가릴 수 없다 — **멈추고 사람에게 넘긴다.** 디렉터리가 남아 있으면 `remove` 가 `is not a .git file,
  error code 7` 로 거부하고 `prunable` 도 아니라 `prune` 도 안 듣는다 — 사람이 `.git/worktrees/<id>` 를 직접
  치워야 한다(실측). 디렉터리까지 없으면 `prunable` 이 붙어 3번 `remove` 가 exit 0 으로 등록만 지운다.
  (HEAD 가 **없는 커밋**을 가리키는 등록은 HEAD 자체는 읽히므로 여기 안 걸린다. 대신 레포 전체의 `git fetch`
  를 죽인다 — SKILL.md 2단계의 `fetch` 갈래에 있다.)
- `dangling yes` — `branch` 줄은 있는데 HEAD 가 0이다: **브랜치 ref 가 지워지고 등록만 남은 잔재**로, 이 절차가
  치우라고 있는 바로 그 상태다(앞머리 "브랜치 이름이 없으면 먼저 받는다"). **막지 않는다.** `prunable` 이 함께
  있으면 디렉터리도 없는 것이라 3번 `remove` 가 exit 0 으로 등록만 지운다. 디렉터리가 남아 있으면 3번 `remove`
  가 `contains modified or untracked files` 로 거부하는데(HEAD 를 못 읽어 전부 미커밋으로 보인다 — 실측), 그건
  "커밋 전에 중단된 실작업"이 아니다 — 그 사실과 함께 사람에게 넘긴다.
- `container out` — `<레포 루트>/.claude/worktrees/` 밖이다. 이 워크플로가 만든 게 아니니 **지우기 전에
  확인받는다** — 이름이 우연히 규약과 같아도(`/tmp/fix+322-arrow`) 그것만으로 우리 것이라고 보지 않는다.
- `locked` — **지우지 않고 보고한다**(위 "답과 무관하게 지키는 것"). 머지가 증명됐더라도 그 안에 선
  세션의 셸을 죽일 수 있다.
- `detached` — **멈추고 묻는다.** 사람이 bisect 중일 수 있다. 그 레코드가 detached 임을 보여 주고
  "그래도 지워라"는 답을 받았을 때만 넘어간다(위 "답과 승인은 그때 보여 준 출력에 붙는다").

`prunable` 은 막지 않는다 — 사람이 Finder 등에서 디렉터리를 지운 등록이다. 디렉터리가 정말 없으면 3번
`remove` 가 exit 0으로 등록만 지운다(git 2.50.1 실측). 그 자리에 디렉터리가 되살아났으면 `remove` 가
`validation failed … '.git' does not exist` 로 실패하므로 3번의 그 갈래(`prune`)로 간다.

### 1. 안에 서 있는지 본다

```
bash "<사본>/scripts/inside.sh" "<대상 path>"
```

- `OUTSIDE` — 2번으로.
- `INSIDE` — 이 세션의 cwd 가 지울 워크트리 안(또는 그 하위)이다. **이 세션에서 지운다** — 안에 선 채
  3번 `remove` 를 치고, 곧바로 `ExitWorktree(keep)` 로 나가고, 나간 자리를 확인한 뒤에 사후 확인으로 간다
  (순서의 근거는 위 "먼저 알아 둘 것", 나가는 절차는 3번 "안에서 지웠을 때 나가기"). PR 을 만든 세션에서
  곧바로 "머지했어"를 받는 가장 흔한 흐름이 여기로 온다. 2번으로 가기 전에 **나갈 수 있는 세션인지 본다** —
  둘 다 맞아야 한다:
  - 이 대화에 `EnterWorktree` 를 불러 `Entered worktree at <이 경로>` 를 받은 기록이 있다(SKILL.md 2단계 생성,
    이어받기 1번, 6단계 재진입이 그 자리다). 없으면 세션 자체가 그 워크트리 안에서 열린 것일 수 있다(`claude`
    를 그 디렉터리에서 실행한 경우 — 시작 때의 작업 디렉터리가 곧 그 워크트리다).
    **잠들었다 다시 열린 세션도 이 기록으로 본다.** 백그라운드 세션은 일을 마치고 60분 동안 입력이 없으면
    프로세스가 내려가고, 다시 말을 걸면 새 프로세스가 같은 대화를 이어 간다. 새 프로세스는 잡 상태 파일(아래 3번
    "다시 열기 안내")의 `cwd` 에서 뜨지만, 관측에서 세션이 선 자리는 마지막으로 `EnterWorktree` 한 워크트리였다.
    PR 뒤 머지까지 한 시간이 넘으면 "머지했어"를 받는 세션은 대개 이 경우다. 새 프로세스는
    `EnterWorktree` 를 부른 적이 없지만 대화 기록에 남은 것으로 맞는 것으로 친다 — 그런 프로세스의 첫
    `ExitWorktree` 는 기록된 세 번(안에서 지우고 나간 한 번, 지우지 않고 나간 두 번) 모두 받아졌고, 지우고 나간
    한 번은 본 체크아웃으로 돌아와 정리를 끝까지 마쳤다. 지우지 않고 나간 두 번은 곧 그 워크트리로
    되돌려졌다 — 위 "먼저 알아 둘 것"의 순서(지운 뒤 나간다)가 막는 경우다. 브랜치 없는 임시 워크트리를 만들어
    옮긴 뒤 대상을 밖에서 지우는 우회는 쓰지 않는다 — 갈래를 이 하나로 두려는 것이고, 그 우회를
    그때그때 쓰다가 임시 워크트리 하나를 여러 세션이 함께 써서 한 세션이 다른 세션이 처음 뜬 자리를 지운 일이
    있었다.
  - 그 뒤로 이 대화에서 `ExitWorktree` 를 부른 적이 없다. 한 번 나갔다 하네스가 되돌린 세션은 두 번째 나가기가
    `No-op` 으로 거부된다(위 "먼저 알아 둘 것").
  하나라도 어긋나면 `ExitWorktree` 가 `No-op` 으로 거부되어 `remove` 뒤 cwd 를 되돌릴 길이 없으니 **멈추고**, 본
  체크아웃(`<레포 루트>`) 안에서 레포 이름을 붙여 다시 불러 달라고 요청한다. 이 확인은 대화 기록에 기대므로 확실하지 않고(요약으로
  잘린 기록은 못 본다), 둘 다 맞아도 나간 자리가 온전하다는 보장은 아니다 — `EnterWorktree(path:)` 로 워크트리를
  옮겨 다닌 세션은 **직전 워크트리**로 돌아가는데 그것이 그 사이 지워졌을 수 있다. 한 프로세스 안에서
  `EnterWorktree` 를 두 번 불러 옮긴 경우는 관측이 없다(여덟 번의 통과는 모두 한 번만 들어간 세션이었다). 다시
  열린 세션이 대상 워크트리에서 다른 워크트리로 옮겨 갔다가 나간 세 번은, 직전에 서 있던 대상 워크트리가 지워진
  뒤 모두 본 체크아웃으로 돌아왔다(위에서 쓰지 않기로 한 임시 워크트리 우회의 기록이다). 그중 한 번은
  임시 워크트리를 지우지 않고 나가 곧 그 안으로 되돌려졌다 — 위 "지우지 않고 나간 두 번"의 하나와 같은 일이다.
  놓친 것은 `remove` 뒤 `ExitWorktree` 의 `No-op` 이나 `same-repo.sh` 의
  `CWD_GONE` 에서 잡혀 3번 "멈출 때"로 간다. 워크트리는 그때 이미 지워졌고 나머지는 새 세션 몫이 되므로, 여기서
  한 번 보는 값이 있다. 통과하면 2번으로.
- `CWD_GONE` — cwd 가 이미 지워졌다(다른 세션이 이 워크트리를 지웠을 수 있다). 멈추고 보고한다.

### 2. 워크트리 안에서 도는 작업 멈추기

지운 뒤에도 워크트리 안에서 도는 프로세스가 있으면 그 경로에 파일을 다시 써서 디렉터리를 되살린다 — 이 세션이
띄운 테스트면 `__pycache__/`·`.pytest_cache/`, `uv sync` 면 `.venv/`, JetBrains IDE(PyCharm 등)면 `.idea/` 다.
**이 세션이 그 경로 안에서 띄운 백그라운드 작업**(`run_in_background` 로 띄운 `uv sync`·`uv run pytest`, 그 경로를
보는 Monitor)이 아직 돌면 끝나기를 기다리거나 `TaskStop` 으로 멈춘다. `<경로>` 는 0번이 정한 대상 `path`, 4번에서
부를 때는 그 고아 경로다.

**JetBrains IDE 가 떠 있으면 `<경로>` 를 연 창이 있는지 사람에게 묻는다.** 본 체크아웃은 워크트리가 쥔 브랜치를
체크아웃할 수 없어서, PR 의 코드를 보거나 돌려 보려고 개발자가 워크트리를 IDE 로 열어 두는 일이 흔하다. 열린 채
지우면 IDE 가 `.idea/` 를 다시 써 디렉터리를 되살리고, 4번이 지워도 또 살아난다(재 보지는 않았다 — 다른 IDE 가
지운 워크트리 자리에 프로젝트 파일을 되살린 일이 있어 둔 확인이다). 떠 있는지는 IDE 본체 실행 파일로 본다 — 앱
이름만으로 찾으면 IDE 에 딸린 런타임(`Contents/jbr`)으로 도는 보조 프로세스까지 걸려, IDE 를 닫은 뒤에도 묻고
출력이 매번 달라진다. 앱 이름이 아니라 앱 꾸러미 안의 본체 자리(`<앱>.app/Contents/MacOS/<실행 파일>`)를 보므로
`PyCharm CE.app` 같은 판도 잡는다. 실행 파일 이름은 PyCharm 이 `pycharm`, 데이터 작업용 파이썬 IDE DataSpell 이
`dataspell` 이고, 파이썬 플러그인을 얹어 같은 `.idea/` 를 쓰는 같은 회사의 다른 IDE 가 `idea` 다(`dataspell` 은
이름만 더했고 실물로 재 보지는 않았다):

```
pgrep -fl '\.app/Contents/MacOS/(pycharm|idea|dataspell)( |$)'
```

출력이 없으면 떠 있지 않으니 묻지 않는다. 떠 있으면 `<pid> /Applications/PyCharm.app/Contents/MacOS/pycharm` 꼴
줄이 나온다(이 패턴이 본체 자리만 잡고 `Contents/jbr` 아래 프로세스와 `ideas` 처럼 이름이 이어지는 실행 파일은
넘기는 것은 같은 이름의 가짜 프로세스로 확인했다. IDE 를 띄워 재 보지는 않았다). 그때 `<경로>` 를 연
창이 있으면 닫아 달라고 한다. 이 세션이 사람의 요청으로 그 워크트리를 IDE 에 열었으면 그 창부터 닫아 달라고 한다.
**답을 받으면 바로 다음 삭제로 가지 않고** 아래 마지막 문단의 "이어 가는 자리" 대로 다시 돈다 — 묻고 기다린 것이라
그 사이 대상이 바뀌었을 수 있다(위 "먼저 알아 둘 것"). 띄운 작업도 떠 있는 IDE 도 없으면 이 항목은 할 일이 없다.
4번에서 고아 경로로 불렀어도 IDE 가 떠 있으면 묻는다 — 그 자리를 되살린 것이 열린 IDE 일 수 있고(이어받기의
`already exists` 도 그렇다), 4) 의 `rm -rf` 뒤에는 다시 판정하는 단계가 없다. 본 체크아웃에 IDE 를 열어 둔 채 고아
경로가 여럿이면 경로마다 묻게 되는데, 그 소음은 감수한다.

**멈추지 못하면 다음 삭제로 넘어가지 않는다** — 제거 대상이면 3번 `remove`, 4번에서 불렀으면 그 4) `rm -rf`
다. 그 작업과 멈추지 못한 이유를 보여주고 묻는다. 다른 세션이나 사람 터미널에서 도는 프로세스는 여기서 보이지
않는다. 그런 프로세스가 디렉터리를 되살리면 4번이 판정한다(비었거나 `.DS_Store` 뿐이면 치우고, 그 밖이면 목록을
보여 주고 묻는다). **이어 가는 자리**는 — 위 IDE 창 질문이든 이 질문이든 — 위 "먼저 알아 둘 것"의 규칙대로다.
**제거 대상 워크트리로 불렀으면 0번 ②부터 다시 돈다** — 기다리는 사이 detached·다른 브랜치로 바뀐 워크트리를 낡은
대상 그대로 지우지 않게 한다. 4번에서 고아 경로로 불렀으면 4번의 그 경로 1)부터 이어 간다.

### 3. 워크트리 제거

**먼저 `remove` 가 함께 지울 무시 대상 파일을 본다.** `remove` 는 추적 안 된 파일이 있으면 거부하지만
`.gitignore` 대상은 묻지 않고 디렉터리째 지운다. 이 레포의 무시 대상에는 그림 출력 폴더(`diagrams/`)나 편집기
설정(`.vscode/`)처럼 다른 곳에 없을 수 있는 것이 들어 있다:

```
bash "<사본>/scripts/ignored-check.sh" "<대상 path>"
```

이 확인은 **`remove` 바로 앞에서 치고, 둘 사이에 다른 명령을 끼우지 않는다** — 판정은 친 순간의 것이다. 다른
세션이나 사람 터미널에서 도는 프로세스가 그 틈에 무시 대상 파일을 쓰는 것까지는 막지 못한다(2번이 그런
프로세스를 볼 수 없는 것과 같은 한계다).

- `CLEAN` — 무시 대상이 없거나 다시 만들 수 있는 것(`__pycache__`, 최상위의 `.venv`·테스트 캐시·JetBrains IDE
  산출물, 하네스의 `.claude/settings.local.json`, SKILL.md 4단계의 셈 기록 파일, 빈 디렉터리 등 — 스크립트 머리말)뿐이다. 아래
  `remove` 로 간다.
- `KEEP` — **이 절차는 지우지 않는다.** `keep` 줄을 보여 주고, 사람이 그 파일을 옮기거나 직접 지운 뒤 다시
  부르게 한다. "그냥 지워라"는 답이어도 같다 — 디렉터리 줄(`tools/.venv/`)은 그 안을 통째로 가리켜서 답한 뒤에
  안에 새로 생긴 것이 목록에 드러나지 않고, `keep-more 20+` 면 목록이 전부도 아니다. 정리했다는 답을 받으면 위
  "먼저 알아 둘 것"의 규칙대로 다시 돌고(0~3번에서 물었으니 0번 ①을 본 뒤 ②부터), 이 확인이 `CLEAN` 일 때만 `remove` 로 간다(이 갈래에는
  "같은 출력이면 답대로 간다"를 적용하지 않는다 — 3번 `contains modified` 갈래와 같다).
- `MISSING` — 그 경로에 아무것도 없다(디렉터리가 사라진 prunable 등록). 지울 파일이 없으니 아래 `remove` 로 간다.
- `NOT_WORKTREE` — 판정하지 못했다. **0번 ③ 블록에 `prunable` 이 있을 때만** 아래 `remove` 로 간다 — `.git`
  없이 되살아난 디렉터리라 `remove` 가 `validation failed` 갈래로 가서 등록만 치우고, 남은 파일은 4번
  `orphan-check.sh` 가 보여 주고 묻는다. `prunable` 이 없으면 멈추고 그 출력과 블록을 보여 준다 — 무엇을 지울지
  보지 못한 채 `remove` 가 성공하면 무시 대상이 그대로 사라진다.

그다음 `path` 줄의 절대경로를 그대로 옮겨 친다:

```
git worktree remove -- "<대상 path>"
```

**exit 0이면 곧바로 아래 "사후 확인"으로 간다** — 그 사이의 접미사 갈래는 읽지 않는다. 이미 지운 뒤에
접미사로 또 치면 매칭 0개가 되어 cwd 폴백이 남의 워크트리를 잡을 수 있다. **1번이 `INSIDE` 였으면 사후 확인
앞에 아래 "안에서 지웠을 때 나가기"를 먼저 한다** — 접미사 형태로 지웠어도 같다.

**`is not a working tree` 로 실패하면** 등록 형태(NFD)가 어긋났거나 그 사이 등록이 사라진 것이다.
목록을 새로 떠서 가린다:

```
bash "<사본>/scripts/find.sh" "<스냅숏>" "<브랜치>" "<대상 path>"
```

- `FOUND` — 등록은 그대로다. **블록을 0번 ④대로 다시 본다** — `FOUND` 는 detached 레코드도 포함하고,
  0번 ④ 뒤에 누가 그 안에서 bisect 를 시작했거나 잠갔을 수 있다. 걸리면 거기서 멈추고(0번 ④에서 받은 답은
  블록이 그때와 같을 때만 쓴다), 통과하면 접미사를 받는다:

  ```
  bash "<사본>/scripts/suffix.sh" "<스냅숏>" "<대상 path>"
  ```

  - `SUFFIX <접미사>` — **먼저 이 번호 앞머리의 `ignored-check.sh` 를 한 번 더 친다** — 첫 `remove` 뒤
    `find.sh`·`suffix.sh` 가 끼어 앞의 판정이 낡았다. 다시 친 결과는 앞머리 갈래를 그대로 따른다: `CLEAN`·
    `MISSING` 이면 바로 이어 `git worktree remove -- "<접미사>"` 를 치고, `KEEP` 이면 멈춘다. `NOT_WORKTREE` 면 방금
    받은 `find.sh` 블록에 `prunable` 이 있을 때만 이어 치고, 없으면 멈춘다. exit 0이면 아래 사후 확인으로. 또
    `is not a working tree` 면 경합이 도는 중이다 — 아래 "되돌기 한도"대로 0번 ③부터 다시 돈다.
  - `NON_ASCII`·`NO_UNIQUE_SUFFIX`·`UNSAFE` — 접미사로는 안전하게 못 잡는다. **멈추고 사람에게
    넘긴다.**
  - `GONE`·`AMBIGUOUS`·`MAIN` — 그 사이 목록이 바뀌었다. 되돌기 한도대로 0번 ③부터 다시 돈다.
- `GONE` — 그 경로의 등록이 사라졌다. **"이미 제거됐다"로 넘기지 않고** 되돌기 한도대로 0번 ③부터 다시
  돈다 — 다른 바이트 형태로 다시 등록됐을 수 있고, `find.sh` 가 이름·`branch` 줄로 다시 찾는다. 거기서
  `NONE` 이면 정말 없는 것이니 4번으로 간다.
- 그 밖(`MISMATCH` 등) — 멈추고 블록을 보여주고 묻는다.

**되돌기 한도:** 3번에서 0번 ③으로 되돌아가는 것은 한 절차에서 **한 번뿐**이다. 두 번째로 되돌아갈
자리에 오면 멈추고 지금까지 본 출력을 보여주고 묻는다 — 경합이 계속되는 상황이면 되돌기만 반복하고, 그
사이 목록이 계속 바뀌어 어느 판단도 유효하지 않다. **사람의 답을 받아 다시 도는 것(위 "먼저 알아 둘 것")은
이 한도에 세지 않는다** — 한도는 사람 없이 스스로 되도는 횟수이고, 세면 사람이 답하자마자 또 묻게 된다.

**다른 메시지는 접미사로 바꿔도 똑같으니 재시도하지 않는다:**
- `locked` — 그 사이 누가 잠갔다. 0번 ④의 `locked` 규칙대로 지우지 않고 보고한다.
- `is a main working tree` — 그 사이 본 체크아웃이 그 브랜치를 쥐게 됐다. 멈추고 `git switch main` 을
  요청한다.
- `validation failed, cannot remove working tree: '…/.git' does not exist` — **디렉터리가 되살아난 prunable
  등록**이다. 사람이 디렉터리를 지운 뒤 그 자리에 무언가 다시 쓰인 경우이고(Finder 의 `.DS_Store`, JetBrains IDE 의 `.idea/` 등), 0번 ③ 블록에
  `prunable` 이 붙어 있다. `remove` 로는 못 지우므로(git 2.50.1 실측) **등록만 치운다.** 이 등록은 0번에서
  승인받은 대상 그 자체라, 아래 조건이 맞으면 묻지 않고 치운다(5번 ③의 남의 등록과 다르다):
  1. `bash "<사본>/scripts/find.sh" "<스냅숏>" "<브랜치>" "<대상 path>"` 로 그 레코드가 **아직
     `prunable` 인지** 본다. 아니면 prune 하지 않고 되돌기 한도대로 0번 ③부터 다시 돈다 — 아래 3.의 "줄이
     하나면 그게 대상"이 대상의 prunable 에 기대기 때문이다.
  2. `git worktree prune --dry-run -v` 로 무엇이 지워지는지 본다. 출력은 경로가 아니라
     `Removing worktrees/<id>: <이유>` 꼴이다(실측).
  3. **줄이 딱 하나일 때만** `git worktree prune` 한다 — 대상이 prunable 이니 이 목록에 있고, 줄이 하나면
     그 하나가 대상이다. 줄이 여럿이면 출력을 그대로 보여주고 묻는다 —
     `prune` 은 레포 전체에 돌아 디렉터리가 없는 모든 등록을 지운다(비가역, `rm -rf`·원격 삭제와 같은 취급).
     **id 로 대상을 알아보려 하지 않는다** — 같은 이름이 먼저 등록돼 있었으면 숫자가 붙어(`fix+1-a1`)
     대상인데도 다른 것으로 읽힌다(실측).
  `prune` 이 exit 0이면 아래 사후 확인을 그대로 돌리고(`REMOVED` 여야 한다), 남은 디렉터리는 4번이
  `orphan-check.sh` 로 판정해 치운다. 1번이 `INSIDE` 였어도 여기서는 나가지 않는다 — `prune` 은 등록만
  지워 cwd 가 남아 있고, 그 디렉터리는 4번 2)가 `INSIDE` 로 멈춘다.
- `contains modified or untracked files` — **커밋되지 않은 변경**(추적 안 된 신규 파일이든 수정된 추적
  파일이든)이 있다. `.gitignore` 에 있는 것(`__pycache__/`·`.venv/`·최상위 `build/`·`.idea/`·`.DS_Store`·`scratchpad/`)은
  제거를 막지 않으므로, 막고 있는 건 커밋 전에 중단된 실작업이다. (무시 대상은 막지 않는 대신 묻지 않고 함께
  지워진다 — 그래서 위에서 `ignored-check.sh` 로 먼저 봤다.) **`--force` 를 쓰지
  않고**(그 작업이 사라진다) 사람에게 알린다. **어떤 답으로도 `--force` 를 쓰지 않는다** — "그냥 지워라"는
  답이어도 사람이 그 변경을 직접 정리(커밋·삭제)할 때까지 멈추고, 정리했다는 답을 받으면 위 규칙대로 0번
  ②부터 다시 돈다. 이 메시지에는 "같은 출력이면 답대로 간다"를 적용하지 않는다. **블록에 `dangling yes` 가
  있으면 이 메시지는 미커밋 작업 때문이 아니다** — HEAD 를 못 읽어 전부 미커밋으로 보이는 것이니(0번 ④) 그
  사실과 함께 넘긴다.
- `is not a .git file, error code 7` — HEAD 를 못 읽는 등록(파일이 없거나 0바이트)에 디렉터리가 남아 있는
  경우다. `remove` 로도 못 지우고 `prunable` 이 아니라 `prune` 도 안 듣는다(실측) — 멈추고 보고한다. 사람이
  `.git/worktrees/<id>` 를 직접 치워야 한다.
- `fatal: bad object HEAD` 나 `failed to run 'git status'` — HEAD 가 가리키는 커밋이 없는 등록이다(force-push
  뒤 gc 된 커밋). `remove` 로는 못 지운다(실측) — 멈추고 보고한다.
- 여기 없는 메시지 — 그대로 보여주고 묻는다. 재시도해도 되는 건 `is not a working tree` 하나뿐이다.

**안에서 지웠을 때 나가기** — 1번이 `INSIDE` 였고 `remove` 가 exit 0 으로 끝났을 때만 한다. cwd 가 방금
지워졌으니 Bash 를 더 치지 않고 **바로 `ExitWorktree(keep)` 를 부른다** — 사후 확인은 나간 뒤에 한다(스냅숏은
본 체크아웃의 `scratchpad/` 에 있어 살아 있고, 스크립트는 절차 앞머리에서 떠 둔 `<사본>` 에 있다). 그다음 순서대로
확인하고, 걸리면 거기서 멈춘다:
1. **`ExitWorktree` 의 결과 메시지를 본다.** 정상은 `Session is now back in <경로>` 다(뒤에 붙는 "Your work is
   preserved at …" 는 `keep` 의 고정 문구라 디렉터리가 이미 없어도 나온다 — 실측). **`No-op: there is no active
   EnterWorktree session to exit` 면** 이 세션이 `EnterWorktree` 로 들어온 게 아니었거나 하네스 동작이 바뀐 것이다
   — 아래 "멈출 때"로.
2. **돌아온 자리가 이 레포 안인지 본다:**

   ```
   bash "<사본>/scripts/same-repo.sh" "<레포 루트>"
   ```

   `SAME_REPO` 면 아래 사후 확인으로 간다 — 이제부터 Bash 마다 `Shell cwd was reset to <그 경로>` 가 붙는 게
   정상이다. `SAME_REPO` 가 본 체크아웃으로 돌아왔다는 뜻은 아니다 — `.claude/worktrees/` 아래의 등록 없는 빈
   폴더로 돌아가 `SAME_REPO` 가 나온 예외가 한 번 있었다(위 "먼저 알아 둘 것"). 같은 레포 안이면 정리는 그대로
   끝까지 간다. **`SAME_REPO` 가 아니면 어느 것이든 아래 "멈출 때"로** — 다섯 항목 보고까지가 이 갈래의 할 일이다.
   **종료 코드가 0 이 아니어도 값과 상관없이 "멈출 때"로 간다**(3 이면 대개 돌아온 자리의 git 이 "레포가 아니다"
   밖의 이유로 실패한 것이다).
   `remove` 가 이미 끝난 자리라, 일반 규칙(SKILL.md "스크립트를 부르는 법" — 멈추고 stderr 를 보여 준다)만 따르면
   다음 세션에 넘길 다섯 항목 보고가 빠진다. stderr 는 그 보고에 함께 적는다.
   - `NOT_IN_REPO`·`OTHER_REPO` — `ExitWorktree` 가 레포 밖으로 돌려놓은 것이다. 세션을 홈 디렉터리처럼 레포 밖에서 열고
     `cd` 없이 워크트리에 들어간 경우가 그럴 수 있다. **아직 관측은 없다** — 여덟 번의 통과는 전부 본 체크아웃으로
     돌아왔고, 그 뒤 다른 자리로 돌아간 예외 하나도 같은 레포 안이었다(위 `SAME_REPO` 갈래). 그 조건에서는
     `EnterWorktree` 자체가 거부되기도 한다(진입이 거부된 시도는 이 순서에
     오지도 않는다). 이 갈래는 그 조건에서 진입이 됐을 때를 위해 둔다.
   - `CWD_GONE` — 돌아갈 곳이 없거나 돌아간 곳이 지워진 것이다. 세션이 그 워크트리 안에서 열렸거나(1번의 확인이
     놓친 경우), 워크트리를 옮겨 다닌 세션이 이미 지워진 직전 워크트리로 돌아간 경우다.
   `git -C` 나 `cd` 로 우회하지 않는다(위 "먼저 알아 둘 것").

**다시 열기 안내** — 이 갈래를 탔으면 이 정리의 마지막 보고에 넣는다. 끝까지 갔든 아래 "멈출 때"로 갔든 같다.
백그라운드 세션이 잠들었다 다시 열릴 때(제거 절차 1번) Claude Code 는 내부 잡 상태 파일(`~/.claude/jobs/<잡 id>/state.json`)의
`cwd` 에서 새 프로세스를 띄운다. 그 폴더가 방금 지운 워크트리면 다시 열기가 거절될 수 있다 — Claude Code 2.1.287
에서 한 번 거절됐고, 그 폴더가 없는데도 다시 열린 기록도 있다. 그 파일이 어느 폴더를 가리키는지는 이
절차가 보지 않으므로(내부 파일이고, 백그라운드 세션이 아니면 없다) 이 갈래를 탔으면 늘 넣는다. 서 있지 않던
워크트리를 밖에서 지웠는데 그것이 그 `cwd` 인 경우는 놓친다 — 알고 둔 한계다. 넣을 내용은 둘이다:
- 이 세션은 잠든 뒤 다시 열리지 않을 수 있으니, 다음 일은 새 세션에서 한다.
- 다시 열기가 거절되면 거절 메시지(`working directory no longer exists or is not accessible: <경로>`)에 나온
  경로에 빈 폴더를 만들면 열린다 — 거절됐던 세션이 그렇게 다시 열렸다. 지운 워크트리 경로가 아닐 수 있으니
  메시지의 경로를 쓴다. 그 폴더가 `.claude/worktrees/` 아래면 git 에 등록되지 않은 빈 디렉터리라 다른 정리가
  지울 수 있다 — 같은 경로를 대상으로 한 머지 정리의 4번은 빈 디렉터리를 묻지 않고 지우고, 이름이 어느 이슈
  번호와 맞으면 그 이슈의 `/issue` 가 잔재(`orphan`)로 잡는다. 지워졌으면 다시 만든다. 그 폴더에서 다시 열린
  세션은 다른 레포로 `cd` 해 옮겨 가지 못한 기록이 있다. 세션을 더 쓰지 않게 되면 `rmdir` 로 지운다.

**멈출 때** — 워크트리 자체는 이미 지워졌다(`remove` 가 exit 0). 남은 것은 사후 확인·4~6번·(e)이고 이 세션에서는
못 한다. **새 세션은 이 대화를 모른다** — 보고가 그 세션이 대상을 다시 특정하는 데 필요한 것을 전부 담아야
한다. 다섯을 적고, 위 "다시 열기 안내"도 함께 넣는다(이 세션은 작업 디렉터리를 잃었을 수 있어 다시 열기가 거절되기
가장 쉽다):
- **대상을 특정하는 값** — 브랜치 이름, 이슈 번호, 7단계에서 왔으면 PR 번호까지. 머지 정리는 PR 번호나 이슈
  번호로만 시작하고(merge-cleanup.md "대상 브랜치와 이슈 번호를 특정한다") 거기서 브랜치를 다시 찾는다.
  디렉터리 이름에서 브랜치를 추측하는 것은 이 문서가 금지하므로, 이 값이 빠지면 새 세션은 4~6번의 대상을 정할
  수 없다.
- `remove` 는 exit 0 으로 끝났고, 친 인자가 무엇이었는지(`path` 줄의 절대경로였는지 `suffix.sh` 의 접미사였는지).
- **이번 `remove` 의 사후 확인은 못 했다**는 것과, 그것을 새 세션이 해야 한다는 것. 사후 확인은 엉뚱한 것을
  지웠는지(`STILL_PRESENT`)를 가리는 유일한 방벽이고, 접미사로 지웠으면 특히 그렇다(위 "먼저 알아 둘 것").
- 그 사후 확인에 필요한 값 둘 — `<스냅숏>` 경로와 `<대상 path>`. 스냅숏은 본 체크아웃 `scratchpad/` 에 남아 있다.
- 본 체크아웃(`<레포 루트>`) 안에서 새 세션을 열어 **들어온 입구 그대로, 레포 이름과 번호와 위 두 값을 붙여**
  다시 불러 달라는 요청 — 새 세션은 사람이 붙여 넣는 문구만 보므로 **부를 문구를 통째로 적어 준다.** 7단계에서
  왔으면 `머지했어 <레포 이름> PR #<PR번호> — 앞선 세션이 remove 까지 했고 사후 확인은 못 했다. 스냅숏 <스냅숏>, 대상 <대상 path>`,
  2단계 잔재 정리에서 왔으면 `/issue <이슈번호> <레포 이름>` 뒤에 같은 꼬리를 붙인다(잔재 조사가 다시 묻고 "버려"로
  이 절차에 온다). `<레포 이름>` 은 이 레포의 GitHub 이름이다 — 빠지면 새 세션이 SKILL.md "어느 레포 작업인지"에서
  어느 레포인지부터 묻는다. 번호 없는 "머지했어"는 새 세션이 대상을 물어야 해서 왕복이 하나 더 들고,
  "머지했어"로 부른 머지된 적 없는 브랜치는 merge-cleanup.md 가 "한 건도 없으면"에서 멈춰 또 하나 더 든다.
새 세션이 그 꼬리로 할 일은 위 "먼저 알아 둘 것"의 "앞선 세션의 꼬리" 항목에 있다 — 입구에서 레포 루트를 확인한
직후, `residue.sh`·`find.sh` 가 돌기 전에 그 `remove` 의 사후 확인을 한다.

**사후 확인** — exit 0으로 끝난 `remove` 뒤에만 한다(실패한 명령은 아무것도 안 지웠으니 줄이 남아 있는
게 정상이고, 그걸 보고 "다른 것을 지웠다"고 하면 없는 사고를 보고한다):

```
bash "<사본>/scripts/verify-removed.sh" "<스냅숏>" "<대상 path>"
```

기준선은 `<스냅숏>`, 즉 **remove(또는 3번 갈래의 prune) 직전에 돈 `find.sh` 가 뜬 목록**이다. `remove` 는
무엇을 지웠는지 말해 주지 않으므로 이것이 비가역 명령에 대한 유일한 사후 방어다.
- `REMOVED` — 4번으로. `also-gone` 줄이 있으면 다른 세션이 함께 지운 것이니 보고에 적는다. 다만 **`prune`
  뒤에 `also-gone` 이 나왔으면** prune 이 다른 등록까지 지운 것이다 — dry-run 가드상 생기면 안 되는 일이니
  멈추고 그 줄과 함께 보고한다.
- `STILL_PRESENT` — **그 레코드가 그대로 있다. 즉시 멈추고 보고한다.** `gone` 줄이 있으면 **다른 것을
  지운 것**이니 대신 사라진 워크트리를 함께 적는다. `gone` 줄이 없으면 지운 직후 같은 경로가 같은 바이트로
  다시 등록됐거나, prune 갈래였다면 prune 이 아무것도 안 지운 것이다(그 사이 `.git` 이 되살아나 prunable 이
  풀린 경우). **어느 쪽이든 4·5·6번으로 절대 넘어가지 않는다** — 넘어가면 그 워크트리의 주인이 모르는 사이에
  이 브랜치의 원격까지 사라지고, 4번의 `rm -rf` 에는 미커밋 방벽도 없다.
- `REREGISTERED` — 같은 경로가 다른 바이트로 다시 등록돼 있다(누가 지웠다 다시 만들었다). 멈추고
  `gone` 줄과 함께 보고한다.

### 4. 되살아남·고아 확인

지운 자리에 되살아난 디렉터리나 등록 없이 남은 디렉터리를 치운다. 이 번호는 **단독으로 불리는 일이 잦다**
(이어받기의 `already exists`, 잔재 정리의 "고아만", 7단계에서 브랜치 이름을 못 받았을 때). 그렇게 이 절차의
앞머리를 안 지나고 왔으면 `<사본>` 이 없다 — 이 번호의 `<사본>/scripts/…` 는 `<스킬 디렉터리>/scripts/…` 로
읽는다(지울 것이 등록 없는 디렉터리뿐이라 스킬 디렉터리가 사라질 일이 없다). 0번 ③ `NONE` 으로 1~3번을
건너뛰어 왔으면 앞머리는 지났으니 `<사본>` 그대로다.

**대상 경로는 부른 자리가 정한다 — 판별식으로 다시 찾지 않는다:**
- 3번에서 방금 지웠으면 → 그 `대상 path`.
- 재부착이 `already exists` 로 불렀으면 → `add` 에 넘긴 그 경로 하나.
- 사람이 특정 고아를 지목했으면 → `residue.sh` 가 낸 그 줄의 경로. (규약 밖 이름은 판별식에 안
  걸리므로, 다시 찾으면 지목받은 것을 못 찾고 조용히 넘어간다.)
- 그 밖(0번 ③이 `NONE`, 7단계에서 브랜치 이름을 못 받았을 때) → `bash "<사본>/scripts/residue.sh" <이슈번호>`
  의 **`orphan` 줄**, 즉 이 이슈 것만. `other-orphan` 은 지우지 않는다. 여기서 `<이슈번호>` 는 **이슈**
  번호다 — PR 번호를 넣으면 그 번호의 다른 이슈 고아를 지우고 진짜 되살아난 것은 놓친다.

**경로가 없으면 아무것도 하지 않는다** — 빈 값으로 명령을 조립하면 `rm -rf "<레포 루트>/.claude/worktrees/"`
가 되어 다른 이슈의 미커밋 작업까지 지운다.

경로마다 차례로:

1) **판정한다** — `bash "<사본>/scripts/orphan-check.sh" "<경로>"`
   - `MISSING` — 할 일이 없다.
   - `REGISTERED` — **등록된 워크트리 자리다. 절대 `rm -rf` 하지 않는다** — `rm -rf` 에는 `worktree remove`
     의 미커밋 방벽이 없다. 셋째 줄로 갈린다:
     - **`prunable` 줄이 있으면** 디렉터리가 되살아난 죽은 등록이다(사람이 지운 뒤 그 자리에 무언가 다시 쓰인 경우).
       3번의 `validation failed` 갈래와 같이 등록만 치운다 — `git worktree prune --dry-run -v` 의 **줄이 딱
       하나일 때만** `git worktree prune` 하고, 여럿이면 출력을 그대로 보여주고 묻는다. 치기 직전에
       `orphan-check.sh` 를 한 번 더 돌려 **여전히 `REGISTERED` + `prunable`** 일 때만 친다 — "줄이 하나면
       그게 대상"은 이 경로가 prunable 이라는 데 기대는데, 1)의 판정과 dry-run 사이에 바뀌었을 수 있다. 그다음 이 경로를 1)부터 다시 판정한다(등록이 없어졌으니 `EMPTY`·`OTHER_FILES` 중 하나로 나온다).
     - **없으면** 살아 있는 워크트리다. **멈춘다.** 판정 뒤 같은 경로에 새로 등록됐거나(같은 이슈를
       다른 세션이 막 시작한 경우가 전형이다) 사람이 등록된 워크트리를 고아로 지목한 것이다. 살아 있는
       워크트리는 `rm -rf` 가 아니라 제거 절차 0~3번으로만 지운다.
       **이 절차에 브랜치가 없으면**(고아만 치우라는 답으로 왔거나 7단계에서 이름을 못 받았을 때) `find.sh`
       를 부를 수 없다 — 브랜치도 스냅숏 이름도 없다. `orphan-check.sh` 출력만 보여주고 **멈춘다.** 그 경로는
       고아가 아니었고, 어느 브랜치인지 모르면 제거 절차도 돌 수 없다. 사람이 이름을 주면 위 "브랜치 이름이
       없으면 먼저 받는다"로 간다.
       브랜치가 있으면 **묻기 전에 그것이 무엇인지부터 받는다** — `bash "<사본>/scripts/find.sh" "<스냅숏>"
       "<이 절차의 브랜치>" "<경로>"` 로 블록을 받아 `orphan-check.sh` 출력과 **함께 보여주고 묻는다**(첫 줄은
       이 절차의 브랜치를 쥐고 있으면 `FOUND`, 다른 브랜치면 `MISMATCH` 이고 둘 다 정상이다. `MAIN` 이면 그
       경로가 본 체크아웃이고 `MAIN_HOLDS` 면 본 체크아웃이 이 절차의 브랜치를 쥔 것이니 어느 쪽이든 멈추고,
       `GONE` 이면 그 사이 등록이 사라진 것이니 이 경로의 1)부터 다시 돌고, `AMBIGUOUS` 면 블록을 보여주고
       묻는다). 어느 브랜치를 쥔 건지 모른 채 받은 답은 그 등록에 붙지 않는다. 블록에 **`detached` 나
       `unreadable yes` 가 있으면 옮길 `branch` 줄이 없어 이 절차로는 못 지운다** — 그 사실과 함께 보고한다.
       **`branch-escaped` 도 같다** — 옮길 수 없는 이름이다(SKILL.md "인자는 큰따옴표로 감싼다"). 경로끼리 눈으로 맞추지 않는다 —
       문서 첫머리의 이유 그대로다. 답에 따라:
       - **그것도 지우라는 답** — 블록의 `branch` 줄에서 옮긴 브랜치로 제거 절차 **0~3번만** 처음부터 새로
         돌되, 0번 ③은 셋째 인자로 이 경로를 못박고 **그 블록이 답할 때 보여 준 것과 같을 때만** 이어 간다
         (다르면 새 출력을 보여주고 새로 묻는다). **이전 답과
         승인은 쓰지 않는다** — 블록이 승인 때와 바이트까지 같아도 다른 등록이라, 되돌아가 "같은 출력이면
         답대로"를 적용하면 묻지 않고 남의 워크트리를 지운다. 그 브랜치의 5·6번(브랜치·원격 삭제)은 돌지
         않는다 — 사람이 승인한 것은 워크트리 제거이고, 무관한 브랜치일 수 있다. 끝나면 원래 절차의 이 4번으로
         돌아와 **그 경로의 1)부터 다시 판정한다** — 중첩해 돈 0~3번이 지운 자리가 되살아났을 수 있다.
       - **두라는 답** — 그대로 두고 원래 절차를 이어 간다. 그 워크트리가 원래 브랜치를 쥐고 있으면 5번 ③
         `branch -D` 가 막혀 거기서 멈춘다.
   - `OTHER_FILES` — 미커밋 작업일 수 있다(코드든 문서든 리소스든). **지우지 말고** `other` 줄을
     보여주고 묻는다. `other-more 20+` 줄이 있으면 목록이 전부가 아니다 — 20개에서 잘린 것이고(몇 개가 더
     있는지는 세지 않는다 — 남은 체크아웃에 대고 수만 개를 훑으면 멎은 것처럼 보인다), 사람이 전부를 본 게
     아니니 **이 절차는 지우지 않고** 그 디렉터리를 사람이 직접 확인하게 한다. 잘리지 않은 목록을 보고
     "지워도 된다"는 답을 받았으면 **그 경로의 1)부터 다시 돈다**(재개 규칙) — 다시 돈 판정이
     `OTHER_FILES` 이고 `other-more` 줄 없이 `other` 목록이 답할 때와 같으면 묻지 않고 2)로 가고, 달라졌으면 새
     목록을 보여주고 새로 묻는다(`other-more` 줄이 붙었으면 위대로 지우지 않는다).
   - `EMPTY` — 비어 있거나 `.DS_Store` 뿐이다. 둘째 줄이 `container out` 이면 지우기 전에 확인받는다. 2)로.
2) **안에 서 있는지 본다** — `bash "<사본>/scripts/inside.sh" "<경로>"`. `INSIDE`·`CWD_GONE` 이면
   **멈추고 보고한다** — 1번의 "안에서 지운 뒤 나간다" 순서는 여기 쓰지 않는다. `rm -rf` 로 cwd 를 지운 뒤
   `ExitWorktree` 가 받아 주는지는 실측이 없고, 디렉터리가 남은 채 먼저 나가면 하네스가 되돌린다(위 "먼저
   알아 둘 것"). 고아에는 `.git` 이 없어 git 명령이 상위 레포로 올라가 정상 동작하므로, 서 있다는 신호는
   이 확인뿐이다.
3) **2번(도는 작업 멈추기)을 이 경로로 돌린다** — 멈추지 않으면 지워도 다시 생긴다.
4) **`orphan-check.sh` 를 한 번 더 돌린다.** 1)과 삭제 사이에 누가 파일을 넣었을 수 있다. 그 출력이 다음
   둘 중 하나일 때만 `rm -rf "<경로>"` 한다:
   - `EMPTY`
   - `OTHER_FILES` 이고, `other-more` 줄이 없고, 사람이 "지워도 된다"고 답할 때 본 `other` 목록과 **줄까지
     같다**(위 "답과 승인은 그때 보여 준 출력에 붙는다"). `other-more` 줄을 따로 보는 것은, 20개를 보여 주고
     승인받은 뒤 파일이 늘면 새 파일이 21번째 뒤로 가 `other` 줄은 그대로이고 `other-more 20+` 줄만 붙을 수
     있어서다(실측) — `other` 줄만 견주면 새 파일까지 지운다.
   그 밖이면 지우지 않는다 — 목록이 달라졌으면 새 출력을 보여 주고 새로 묻고, `REGISTERED` 면 1)의 규칙대로
   한다. `rm -rf` 에는 `worktree remove` 의 미커밋 방벽이 없어서 이 확인이 유일한 방벽이다.

경로를 다 처리했으면 **이 이슈의 남은 잔재를 보고에 적는다** — 이슈 번호가 있으면 `residue.sh` 를 한 번 더
돌려, 이번에 치운 것 말고 남은 `orphan`·`worktree` 줄(재시도 슬러그 잔재 등)과 `branch-escaped` 줄(이 스킬이
만들지 않은 브랜치)을 최종 보고에 넣는다. 지우지는
않는다 — 사람이 지목하면 그때 이 4번으로 온다. 빼면 "정리 완료"라고 해 놓고 다음 `/issue` 가 `RESIDUE` 로
다시 잡는다.

### 5. 로컬 브랜치 삭제

**3번이든 4번이든 멈춘 채 사람 답을 기다리는 중이면 진행하지 않는다.** 특히 4번이 `REGISTERED` 로 멈춘
경우 — 3번만 보면 통과한 것처럼 보여, 사람이 쓰는 체크아웃 아래에서 브랜치와 원격이 사라진다.

① **브랜치와 detached 워크트리를 먼저 본다** (2단계에서 왔든 7단계에서 왔든):

```
bash "<사본>/scripts/detached-check.sh" "<브랜치>"
```

`ref` 줄이 무엇을 기준으로 봤는지 알려 준다 — 로컬 브랜치(`refs/heads/…`)와 원격 추적 ref(`refs/remotes/origin/…`)
중 있는 것마다 한 줄이고, 어느 한쪽에만 있는 커밋에 선 detached 도 잡는다. 원격에만 남은 브랜치를
`git checkout "origin/<브랜치>"` 로 열어 둔 체크아웃이나, 다른 머신의 push 로 원격이 앞선 커밋에 선 체크아웃도 6번
원격 삭제 앞에서 걸리게 하려는 것이다.
- `NO_BRANCH` — 로컬에도 원격 추적 ref 에도 그 브랜치가 없다. **②·③을 건너뛰고 6번으로 간다 — 6번은 건너뛰지
  않는다.** 로컬 추적 ref 가 없다고 원격에 없는 것이 아니다: 우리 `fetch` 뒤에 다른 머신이 그 이름으로 push
  하면 정확히 이 모양이 되고, 6번이 `ls-remote` 로 서버에 물어야 그 브랜치를 본다. 건너뛰면 원격 브랜치가
  남아 다음 `/issue` 의 `push -u` 를 non-fast-forward 로 막는다 — 6번이 막으려는 바로 그 일이다.
  그 경우 6번은 `fetch` 로 추적 ref 를 만든 뒤 **여기 ①부터 다시 돌려보낸다** — 이 확인은 `NO_BRANCH` 로
  끝나면 detached 워크트리를 하나도 안 보므로, 원격 삭제 앞에 그 방벽을 세우려면 R 이 생긴 뒤 다시 와야 한다.
- `FOUND` — 그 브랜치에만 있는 커밋에 detached 로 선 워크트리가 있다(누군가 bisect 중일 수 있다).
  **지우지 말고** 블록을 보여주고 묻는다. detached 워크트리는 `branch` 줄도 규약 이름도 없어 0번 ③에 안
  걸리므로, 이 확인이 없으면 체크아웃은 살아 있는데 그 아래에서 브랜치와 원격만 사라진다. 0번 ③의
  `DETACHED_CANDIDATES` 에서 이미 보여 준 워크트리가 여기 다시 나올 수 있다 — 묻는 것이 달라서다(거기서는
  "이 브랜치의 워크트리인가", 여기서는 "브랜치를 지워도 되나"). 두 번째라고 건너뛰지 않는다. 그래도 지우라는
  답을 받으면 `NONE` 과 같은 갈래로 이어 간다 — `ref refs/heads/…` 줄이 있으면 ②로, 원격 추적 ref 줄만
  있으면 ②·③을 건너뛰고 6번으로 간다.
- `NONE` — `ref refs/heads/…` 줄이 있으면 ②로. **원격 추적 ref 줄만 있으면** 로컬 브랜치가 없는 것이니 ②·③을
  건너뛰고 6번으로 간다 — 그대로 내려가면 ②의 `git log` 와 ③의 `branch -D` 가 없는 브랜치에서
  `unknown revision`(exit 128)으로 죽어 6번의 원격 정리까지 못 간다.
`unreadable` 줄이 있으면 판정에서 뺀 깨진 등록이다 — HEAD 를 못 읽거나(파일이 없거나 0바이트) 그 커밋을 못
찾는다(force-push 뒤 gc 된 커밋 등). 하나 때문에 판정 전체가 죽으면 그 레포의 머지 정리가 전부 막히므로 빼고
보고만 한다 — 최종 보고에 적는다.

② **원격에 없는 커밋이 로컬 브랜치에 있는지 본다.** 기준은 어디서 왔느냐로 정한다:
- **2단계 잔재 정리에서 왔으면** R이 있으면 `git log --oneline "origin/<브랜치>..refs/heads/<브랜치>"`, R이
  없으면 `git log --oneline "origin/main..refs/heads/<브랜치>"`. 잔재 조사에서 사람이 본 것은 L·R 두 sha뿐이라
  "L이 R보다 앞서 있다"가 화면에 없고, R이 아예 없으면 "원격 없음"으로만 보인다 — 이전 실행이 커밋까지 하고
  `push -u` 전에 죽은 모양이 정확히 그것이다.
- **7단계에서 왔으면** `git log --oneline "<M>..refs/heads/<브랜치>"` — M 은 (a)가 받아 둔 PR
  head(`headRefOid`)다.
  `origin/main` 을 기준으로 삼지 않는다 — squash 머지라 브랜치 커밋은 `origin/main` 의 조상이 **아니어서**
  정상 정리가 매번 걸린다. M 기준이면 머지된 시점까지는 비고 **그 뒤에 얹힌 커밋만** 나온다. (a)는 한 번만
  도는데 사람 답을 기다리는 사이 누가 그 브랜치에 커밋할 수 있어서, 건너뛰지 않고 여기서 다시 본다.
한 줄이라도 나오면 **그 목록을 보여주고 다시 묻는다.** 워크트리가 깨끗하니 3번의 미커밋 방벽도 안 걸리고,
`branch -D` 뒤에는 reflog에만 남는다. 명령이 실패하면(M 을 못 찾는 등) 멈추고 보고한다.

③ `git branch -D "<브랜치>"`. squash 병합 뒤에는 `-d` 가 항상 "not fully merged"로 거부되므로 위 확인을 거친
`-D` 가 정상 경로다.
**`cannot delete branch … used by worktree at <P>` 이면** 어떤 등록이 그 브랜치를 쥐고 있다. 대상 워크트리는
3번에서 이미 지웠으므로 **그 등록은 0번에서 승인받은 레코드가 아니다** — 사람이 `AMBIGUOUS`·
`DETACHED_CANDIDATES` 에서 "그건 아니다"라고 제외한 것이거나 그 사이 다른 세션이 만든 것이다. 그래서
**자동으로 치우지 않는다.** 먼저 P 가 죽은 등록인지 가린다 — `bash "<사본>/scripts/find.sh" "<스냅숏>"
"<브랜치>" "<P>"` 로 그 경로의 블록을 받는다(첫 줄은 `FOUND` 든 `MISMATCH` 든 상관없다. `GONE` 이면 그 사이 등록이
사라진 것이니 `-D` 를 다시 치고, `MAIN` 이나 `MAIN_HOLDS` 면 멈추고 보고한다 — 본 체크아웃이 그 브랜치를 쥐고
있으면 `find.sh` 는 셋째 인자가 있어도 `MAIN_HOLDS` 를 먼저 낸다).
- 블록에 **`prunable` 이 없으면** P 는 살아 있는 워크트리다 — prune 을 제안하지 않고 멈추고 보고한다. dry-run 에
  다른 줄이 있더라도 P 와 무관한 등록이라 치워도 `-D` 는 또 막힌다. **dry-run 의 id 로 P 를 알아보려 하지
  않는다** — 같은 이름이 먼저 등록돼 있었으면 숫자가 붙어(`fix+7-dup1`) 죽은 등록을 살아 있다고 오진한다
  (이전 교차 리뷰에서 실측).
- **`prunable` 이면** P 와 `git worktree prune --dry-run -v` 출력을 보여주고 묻는다. **줄이 딱 하나일 때만**
  치우자고 제안한다 — 여럿이면 P 말고 다른 등록까지 사라진다. prunable 이라도 죽은 등록이라는 보장이 없다 —
  외장 볼륨이 안 붙은 워크트리도 prunable 로 보이는데, prune 하면 볼륨을 다시 붙여도 `git worktree repair` 로
  되살릴 수 없다(이전 리뷰에서 실측). `prune` 은 레포 전체에 돌아 디렉터리가 없는 **모든** 등록을
  지운다(`rm -rf`·원격 삭제와 같은 취급이다). 치우라는 답을 받으면 위 규칙대로 5번 ①부터 다시 돌아 여기 왔을 때
  `find.sh` 블록과 dry-run 이 답할 때 본 것과 같을 때만 `git worktree prune` 뒤 다시 `-D` 한다.

### 6. 원격 브랜치

원격 브랜치가 남아 있으면 **치우고 가야 한다**(자동 삭제가 꺼져 있거나 사람이 남긴 경우, 우리 `fetch` 뒤에
다른 머신이 push 한 경우). **남았는지는 로컬 R 이 아니라 아래 `ls-remote` 로 본다** — 5번이 `NO_BRANCH` 로 와도
6번은 돈다. 남겨두고 새로 시작하면 5단계
push에서 막힌다 — 브랜치 이름은 이슈 번호에서 나오므로 새로 따도 같은 이름이고, 새 브랜치는 `origin/main`
에서 잘라 squash 머지된 원격 팁의 자손이 아니라 `git push -u` 가 non-fast-forward로 거부된다. 구현을 다 끝낸
뒤 첫 push에서 막히는 자리다.

**열린 PR 과 원격 팁을 여기서 한 번 더 본다:**

```
gh pr list --head "<브랜치>" --state open --limit 100 --json number
git ls-remote --heads origin "<브랜치>"
```

PR이 하나라도 나오면 **지우지 않는다.** 원격 브랜치를 지우면 GitHub이 그 PR을 자동으로 닫는다. 0번 ②에서 이미
봤지만 그 사이 1~5번이 도는 동안(사람 답변 대기가 끼면 길다) 누가 PR을 열 수 있고, 되돌릴 수 없는 쪽은
이쪽이라 두 번 보는 값이 있다. 열린 PR이 있으면 그 번호를 짚어 다시 묻는다.

`ls-remote` 줄이 여럿이면 **둘째 칸이 정확히 `refs/heads/<브랜치>` 인 줄만 쓴다** — `ls-remote` 도 접미사로
맞춰서 `fix/5` 로 물으면 `refs/heads/feat/fix/5` 가 함께 나온다(실측). 명령이 **rc 0 이 아니면** 멈추고
보고한다 — 원격에 못 닿으면 출력이 비고 rc 128 이라(실측), rc 를 안 보면 "브랜치가 없다"로 잘못 읽는다.
**팁은 서버에 묻는다.** `git for-each-ref … "refs/remotes/origin/<브랜치>"` 는 **로컬 추적 ref** 라 fetch 하기
전에는 세션 시작 때 값 그대로다 — 그것으로 "그대로인가"를 보면 누가 push 했어도 늘 "그대로"가 나온다
(실측). `ls-remote` 가 낸 sha 가 앞서 받아 둔 R(잔재 조사나 머지 정리의 `for-each-ref`)과 **다르면**
그 사이 누가 그 원격 브랜치에 push 한 것이다 — 지우지 말고 `git fetch origin "refs/heads/<브랜치>"` 로 받은 뒤
`git log --oneline "<R>..origin/<브랜치>"` 로 **그 사이 얹힌 커밋까지 함께 보여주고** 다시 묻는다(lease 에 넣을
값은 그래도 `ls-remote` 가 낸 전체 sha 다). **그 `fetch` 뒤에는 잔재 조사의 `for-each-ref` 한 줄을 다시 돌려
L·R 을 새로 받는다** — 안 받으면 답을 받고 6번 처음부터 다시 돌 때 옛 R 로 또 "다르다"가 된다. 5번 ②는 옛 팁까지만 봤으므로 그 커밋들은 아무도 확인하지 않았다.
`ls-remote` 출력이 비어 있으면(rc 0) 원격 브랜치가 이미 없는 것이니 6번은 할 일이 없다 — 보고에 적고 넘어간다.

**R 이 아예 없는데 `ls-remote` 가 sha 를 내면**(5번 ①이 `NO_BRANCH` 로 보낸 경우가 그렇다) 견줄 값이 없다 —
`git fetch origin "refs/heads/<브랜치>"` 로 추적 ref 를 만들고 **잔재 조사의 `for-each-ref` 한 줄을 다시 돌려
L·R 을 새로 받은 뒤** **5번 ①부터 다시 돈다.** L·R 을 새로 안 받으면 R 이 계속 "없음"이라 이 자리로 돌아와
사람 없이 맴돈다 — `refs/heads/` 를 빼도 같은 모양이 된다(같은 이름의 태그가 있으면 태그만 받고 추적 ref 가
안 생긴다, "먼저 알아 둘 것"). 그래야 R 이 생겨 이 비교가
성립하고, 그 원격 커밋에 선 detached 워크트리도 5번 ①이 본다(`NO_BRANCH` 로 끝난 확인은 아무것도 안 봤다).
그 커밋들은 5번 ②도 못 봤으니, 다시 돌아 여기 왔을 때 보여줄 목록은 2단계에서 왔으면
`git log --oneline "origin/main..origin/<브랜치>"`, 7단계면 `git log --oneline "<M>..origin/<브랜치>"` 다.

열린 PR이 없으면 **비가역 원격 작업이므로 사람에게 확인받는다.** 확인을 받으면 위 "먼저 알아 둘 것"의 규칙대로
6번의 처음(열린 PR 과 `ls-remote`)부터 다시 돌아, 열린 PR 이 여전히 없고 **`ls-remote` 가 확인 때 본 sha 와
같을 때만** 친다:

```
git push origin --delete "refs/heads/<브랜치>" "--force-with-lease=refs/heads/<브랜치>:<그 sha>"
```

`--delete` 에도 `refs/heads/` 를 붙인다 — 맨 이름이면 같은 이름의 태그가 있을 때 `dst refspec … matches more
than one` 으로 죽는다(실측, 아무것도 안 지워진다).
`--force-with-lease` 는 확인과 삭제 사이의 틈을 막는다 — sha 는 `ls-remote` 가 낸 **전체 sha** 를 그대로 옮긴다.
그 사이 누가 push 했으면 `! [rejected]        (delete) -> <브랜치> (stale info)` 로 거부되고 rc 1 로 끝나며
**아무것도 안 지워진다**(실측). 거부되면 지운 게 없으니 6번의 처음부터 다시 돈다.
`error: unable to delete '<브랜치>': remote ref does not exist`(rc 1)면 그 사이 누가 지운 것이니 할 일이 없다 —
보고에 적는다. 0번으로는 되돌아가지 않는다. 거절하면 보고에 남기고 멈춘다 — 다른 슬러그로 우회하면 이름 규약이
깨져 다음 세션의 잔재 탐지가 못 찾는다.
